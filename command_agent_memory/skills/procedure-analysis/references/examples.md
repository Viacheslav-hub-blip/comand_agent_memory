# Примеры выделения самостоятельного опыта

## Case: срез исторических решений и реальный вклад причин

### Диагностика расхождения legacy-агрегата с историческим срезом

#### Обобщённая ситуация

Агрегат использует любое историческое `approved`-событие, хотя корректная метрика требует последнего известного на момент `T` статуса.

#### Как решали в конкретной задаче

- Исходная задача и условия: `legacy_approval.sql` по `applications` и `decision_events`, когорта 1–2 октября 2026, `T=2026-10-03 00:00:00 UTC`, определение `v1`.
- Что сделали: применили `occurred_at < T AND loaded_at < T`, выбрали последнее событие по `occurred_at DESC, event_id DESC`, получили по одной записи на заявку.
- Как проверили: сопоставили исходный результат с согласованным срезом; сравнили шесть строк `approved` с числом уникальных заявок.
- Что получили и статус результата: legacy 6 строк / 85 000; согласованный `v1` — 3 заявки / 27 000. Устаревшие статусы `A002`, `A007` дали 50 000 расхождения, поздняя загрузка `A006` — 8 000. Вклад повторной агрегации одной заявки среди шести строк `approved` равен **нулю**.

#### Связь с новой задачей

Сравни условия измерения обеих сторон и проверяй фактическое влияние `JOIN` уже после всех фильтров. Риск fan-out существует при `1:N`, но его численный вклад зависит от данных и запроса.

## Case: границы DISTINCT

В том же сценарии `DISTINCT` по заявке и сумме сохранил 6 / 85 000, потому что устранение дублей не восстанавливает последнее состояние. Если самостоятельный запрос посвящён именно различию дедупликации и истории событий, выдели отдельный Case с этой проверкой. При общей задаче объяснения legacy-расхождения объедини его с предыдущим Case в одну запись с дополнительным выводом.

## Пример без Skill: восстановление состояния на дату

В диалоге проверили отдельную операцию `occurred_at<T AND loaded_at<T`, выбрали последнее событие по `event_id` и подтвердили A006/A007. Извлеки Case с исходной задачей, предикатами, `event_id=8/9/11`, наблюдаемым результатом и границами применения.

**Раздел `## Skill` опусти:** восстановление одного статуса и узкий SQL-приём не составляют полный бизнес-процесс или сквозную работу от исходных данных до конечного результата.

## Пример полноценного Skill: сверка отчётности от CSV до отчёта

Запрос: «Подготовь воспроизводимый процесс сверки: CSV → схема/SQLite → исторические срезы → заявочные и денежные метрики → объяснение расхождения с legacy → параметризованный SQL и report.md, который можно пересчитать по другой когорте».

Подтверждённая история: применили `schema.sql`, загрузили CSV, исправили логику среза, получили `v1=3/8`, `v2=2/7`, `27 000` и `22 000` запрошенных сумм, отдельно `47 000−23 000=24 000` чистой выдачи по v1; подтвердили остаток `85 000−27 000=58 000` как `50 000+8 000`; создали воспроизводимый SQL и способ запуска, проверили инварианты.

```markdown
## Skill
### Построение воспроизводимой сверки заявочной и денежной отчётности
- Назначение и условие запуска: построить полный процесс от сырых CSV
  и бизнес-определений до воспроизводимых вычислений и отчёта.
- Входы: схема, CSV заявок/решений/платежей, версия определения,
  старый SQL, границы когорты, T, рабочий каталог.
- Основной алгоритм: проверить входы и ключи → собрать локальную БД →
  установить параметры и определения → восстановить as-of-срез →
  посчитать заявочные и денежные показатели → воспроизвести legacy →
  разложить остаток → выпустить SQL, запуск и отчёт.
- Необходимые проверки: одна строка на заявку; корректные условия
  обоих времён; арифметическая сходимость; исходники не изменены;
  повторный запуск на новых параметрах.
- Условные действия: версия или метрика не подтверждена → показать
  неопределённость; остаток не сходится → диагностировать источник;
  нужна независимая реализация → выполнить дополнительную перепроверку.
- Результат и критерий завершения: готов комплект воспроизводимых
  артефактов, расчёты проверены на входах, указаны версии и ограничения.
```

Развёрнутый Skill после консолидации должен включать необходимые рабочие примеры входных CSV, вызовы инструментов, параметризированный SQL и ожидаемые контрольные значения. Исторические числа остаются примерами, а не постоянными значениями для новых запусков.

## Отладка инструментов

Из истории с Windows `cmd.exe` сохрани в Case проверенную особенность оболочки, только если показано, какое конкретное действие надёжно устранило сбой. Длинный список неудачных `python -c`, `ls`, `wc` и временных пробных файлов не образует обязательный метод решения SQL-задачи.
