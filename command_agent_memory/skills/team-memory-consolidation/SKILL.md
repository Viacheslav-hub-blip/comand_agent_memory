# Обновление командного реестра

Вход: текущий реестр с историей решений, принятые личные документы и проверенные
source-ID с владельцами, сессиями и основаниями принятия. Выход: один JSON-объект
с решением и изменениями записей. Файлы не изменяй. Отдельного review нет.

Сопоставляй сведения по смыслу и условиям. Для существующего знания используй его
ID; новое получает устойчивый ID из латинских букв, цифр, дефисов и подчёркиваний.
Сохраняй прежние существенные сведения и бинарные приложения: не обновляй запись
с бинарными документами текстовой заменой. Незатронутые записи не включай в updates.

Для каждого изменения укажи утверждение, известные условия, непустое обоснование,
подтверждающие source-ID и полные самостоятельные Markdown-документы.
Размещай их в wiki/, cases/, skills/. INDEX.md строит приложение. Для точного
копирования принятого документа, включая бинарное приложение, вместо текста
укажи `{"source_id": "ID из evidence_ids этой записи"}`. Приложение возьмёт
проверенные исходные байты; не составляй base64 самостоятельно.
Один активный документ принадлежит одной записи. Если спор затрагивает часть
большого документа, раздели сведения на самостоятельные записи и документы,
сохранив бесспорные сведения и ссылки. Не выполняй разбор Markdown программой.

Статусы:
- accepted: доступных оснований достаточно для заявленных условий, существенного
  неразрешённого противоречия нет. Поясни достаточность в reason.
- pending: оснований или условий недостаточно. Сохрани кандидат и нужное уточнение.
- conflicts: несовместимые утверждения об одном определении при одинаковых
  условиях. Сохрани обе стороны отдельными записями и взаимные conflicts_with.
  Если прежде одна сторона была accepted, обнови её тем же ID до conflicts.

Числового порога и голосования нет. Replay проверяет применение, но не является
новым источником истинности. Повторный анализ одного чата не даёт независимого
подтверждения; сверяй владельца, исходные сессии и происхождение. Неизвестная
независимость остаётся неизвестной. Сведения, скопированные из общей памяти,
не считай независимым подтверждением. Не выдумывай источники.

Новые сведения требуют повторного сопоставления с pending/conflicts. Переводи
их в accepted только при новом содержательном основании: добавь новый source-ID
и объясни, какой пробел или спор он разрешает. Само число упоминаний не решает спор.
Для разрешённого конфликта обнови все связанные стороны; неподтверждённая сторона
может остаться pending с объяснением. Историю прежних решений сохраняет приложение.

Разные корректные определения или методы сохраняй с условиями и кейсами.
Различие формул или таблиц само по себе не означает конфликт.
Личные правила и предпочтения не превращай в командные требования.

Верни ровно один JSON без Markdown:

```json
{
  "decision": "accepted",
  "summary": "Какие знания сопоставлены и что изменилось",
  "findings": [],
  "updates": [{
    "id": "metric-definition-v1",
    "status": "pending",
    "statement": "Определение показателя",
    "conditions": "Известные условия; явно указать неизвестные",
    "reason": "Какое основание есть и чего не хватает",
    "evidence_ids": ["source-ID из входа"],
    "conflicts_with": [],
    "documents": {"wiki/metric-definition-v1.md": "Полный текст документа"}
  }]
}
```

При отсутствии изменений updates пуст. Accepted означает принятие обработки
реестра и допускает наличие pending/conflicts: они не публикуются как память.
Если корректно сопоставить и сохранить записи невозможно, верни needs_resolution,
непустые findings с file/problem/change и updates: []; весь снимок останется прежним.
