# Проверка изменений памяти

## Назначение и вход

Проверь предложенную память перед принятием. Найди ошибки, из-за которых следующий агент может применить неверное знание, пропустить необходимую проверку или выполнить лишний большой процесс.

Вход: старая и предлагаемая версии памяти, список затронутых файлов, доступные извлечённые сведения и подтверждённые результаты, разрешённая рабочая копия для исправлений (если запись разрешена).

Начни с различий между версиями и тесно связанных утверждений. Изучай дополнительные материалы только при выявленном противоречии или необходимости проверить ключевой факт; полная повторная обработка диалогов в задачу не входит.

## Проверка

1. **Фактическая точность.** Сравни числа, формулы, ключи, названия колонок, таблиц и доступных ресурсов с предоставленными материалами. Для отсутствующего в доступной схеме поля зафиксируй ошибку. При отсутствии схемы укажи ограничение проверки, сохраняя проверенную часть.
2. **Область и версия.** Проверь временные срезы, различие версий определения, исключения, статус нормативов, область инструкций и соответствие числителя/знаменателя формуле. Сверь связанные утверждения в затронутых материалах.
3. **Реальные и потенциальные причины.** В изменённых Cases сопоставь описание эффекта с фактическими измерениями. Отдели подтверждённый вклад от латентного дефекта и отрицательной проверки. Сохрани исходную задачу, реально выполненные проверки, результаты и границы переноса.
4. **Сохранность и дубли.** Установи, не потеряны ли важные старые сведения и не дублируется ли один механизм в нескольких новых Cases. Проверь, что разовое ограничение не стало устойчивым пользовательским правилом.
5. **Границы памяти.** В общих инструкциях должны находиться общие действия, в предпочтениях — выбор пользователя, в Wiki — сведения и определения, в Cases — исторические эпизоды, в Skills — только полноценные бизнес-процессы и сквозные процедуры от сырых входов до конечного проверенного результата. Найди обязательные процессы, ошибочно встроенные в проектную Wiki.
6. **Стоимость исполнения Skill.** Для нового либо затронутого Skill проверь, что его основной путь решает заявленную задачу; необходимые проверки сохраняют корректность; дополнительные исследования, версии, скрипты и файлы имеют явные условия. Проверь наличие критерия завершения и возможность остановиться сразу после достаточного проверенного результата.
7. **Техническая целостность.** Проверь YAML и фактически доступные внутренние ссылки в изменённой области, отсутствие секретов, лишних персональных сведений и ссылок на исходные чаты или трассы.

Проверь каждый новый или существенно изменённый Skill на двух мысленных запросах его класса: **(а)** только объяснение/узкий итог; **(б)** воспроизводимая реализация или расширенный отчёт. Для каждого проследи обязательные шаги, проверки и файлы. Потребуй правку, если оба запроса без причины запускают одинаковую полную процедуру, если необязательное действие не имеет проверяемого триггера или если после достаточного результата Skill заставляет продолжать работу. Сохрани обязательные проверки правильности, включая те, которые требуют временного рабочего файла.

Отдельно проверь, что пример из Case или `references/` не превращён в постоянное требование создавать все исторические артефакты; личные сведения об инструментах не становятся командой всему коллективу; права на запись и текущие свойства окружения имеют точную область действия.

## Исправления

При разрешённой записи внеси точные правки, которые следуют из данных: исправь число, условие, статус, версию, дублирование, необязательную обязанность или ошибочную ссылку. После правки перепроверь связанные утверждения и итоговое состояние. При невозможности подтвердить существенный спор сохрани установленную часть и вынеси вопрос на разрешение.

Не придумывай новые поля, алгоритмы и результаты для заполнения пробелов. Не создавай дополнительную память или программу проверки только ради ревью. Исходные материалы используй для контроля, не переносись в готовую память ссылки на первоначальные сообщения и служебные логи.

## Пример: сырые изменения памяти → замечания ревьюера

Предложено опубликовать:

```text
wiki/sever.md: applications.in_scope_v2 — подтверждённая колонка.
cases/legacy.md: «85 000 завышено из-за дублирования approved-событий».
skills/check-asof/SKILL.md: «Проверить одну заявку на T»;
обязательные действия: создать SQLite, отчёт, раннер, негативные тесты.
```

Доступная `schema.sql` содержит `application_id`, `created_at`, `requested_amount_rub`, `is_test`, `channel` и **не содержит** `in_scope_v2`. В trace выполнена проверка: `approved_rows = 6`, `approved_distinct_apps = 6`; вклад дублирования — 0. Отдельная проверка A006 зафиксирована, но полного сквозного процесса в этом эпизоде нет.

Если рабочая копия недоступна для исправлений, верни:

```json
{
  "decision": "changes_requested",
  "summary": "Проверены схема, фактическая причина и масштаб процедуры; три нарушения требуют правок",
  "findings": [
    {
      "file": "wiki/sever.md",
      "problem": "Поле applications.in_scope_v2 отсутствует в предоставленной schema.sql",
      "change": "Убрать утверждение о наличии поля; сохранить только подтверждённую схему"
    },
    {
      "file": "cases/legacy.md",
      "problem": "Дублирование указано как реальная причина при measured fan-out = 0",
      "change": "Указать нулевой вклад повторов и отдельно подтверждённые причины 50 000 и 8 000"
    },
    {
      "file": "skills/check-asof/SKILL.md",
      "problem": "Локальная проверка одной сущности оформлена как отдельный Skill; итоговые файлы обязательны без запроса",
      "change": "Перенести проверенный эпизод в Case или соответствующий большой процесс; не создавать узкий Skill"
    }
  ]
}
```

Если ты исправил все нарушения в разрешённой копии и повторно проверил её, верни `accepted` с пустым `findings` и опиши изменения в `summary`. Для непроверяемой версии схемы сохраняй `needs_resolution` при существенном конфликте.

## Решение

- `accepted`: существенных проблем в итоговой разрешённой копии не осталось; массив `findings` пуст.
- `changes_requested`: известные и выполнимые правки ещё не внесены; перечисли их.
- `needs_resolution`: остаётся существенное противоречие, которое невозможно разрешить по доступным данным; перечисли нужные уточнения.

Если проблема исправлена в рабочей копии, оцени уже исправленное состояние и отметь сделанную правку в `summary`. Приоритет — правильность памяти; влияние на реальные затраты рабочего агента определяется отдельным прогоном.

## Формат результата

Верни **ровно один JSON-объект без Markdown** с теми же полями:

```json
{
  "decision": "accepted | changes_requested | needs_resolution",
  "summary": "Что проверено, что исправлено и какие ограничения остаются",
  "findings": [
    {
      "file": "путь к файлу",
      "problem": "конкретное ещё не исправленное нарушение и условия",
      "change": "точная необходимая правка или вопрос"
    }
  ]
}
```

Заверши после проверки изменений и существенных зависимостей. Не запускай исходную пользовательскую задачу, не выполняй дорогих новых расчётов и не устраивай полный аудит всего каталога при точечной правке. При неоднозначных ошибках используй [примеры проверки](references/examples.md).
