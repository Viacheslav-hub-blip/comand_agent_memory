# Проверочные случаи для ревью памяти

## Версии

Статья утверждает, что `v1` включает тестовые заявки. Новая формула в Skill описывает «реальные заявки», одновременно показывая `3/8` с тестовой A004. Выяви нарушение версии и согласуй: `v1` — 3/8, `v2` — 2/7 для данного снимка.

## Реальный вклад и латентный риск

Case утверждает, что итог 6/85 000 завышен из-за повторного подсчёта одной заявки. Фактическая проверка показала шесть разных заявок среди шести отобранных `approved`-строк. Укажи фактический вклад размножения `0`; сохрани реальные причины разницы v1 с 3/27 000: устаревшие статусы 50 000 и поздняя загрузка 8 000. Саму опасность `1:N` оставь как условный риск.

## Несуществующее поле

Wiki описывает `applications.in_scope_v2`, но предоставленная схема содержит `application_id`, `created_at`, `requested_amount_rub`, `is_test`, `channel`. Зафиксируй ошибку относительно **этой версии схемы**. Не подменяй поле выдуманным алиасом.

## Разовое требование стало глобальным

У Бориса «ничего не устанавливай» относилось к текущему запуску. Постоянный запрет пакетов в `USER_PREFERENCES.md` не подтверждён. Сохрани предпочтение pandas и область временного ограничения.

## Принудительная избыточность

Skill для объяснения legacy-расхождения всегда требует написать полноценный раннер, создать SQLite, запустить независимую реализацию, выполнить мутационные тесты и опубликовать три отчёта. Для типовой задачи достаточно правильного среза, проверки ключей и причин расхождения. Перенеси дополнительные файлы и методы в условные действия с наблюдаемыми триггерами. Сохрани исходные проверки, без которых вывод был бы недостоверен.

## Неявная инструкция в проектной Wiki

Wiki сообщает «для любой диагностики всегда выполняй шесть этапов». Преврати запись в описание факта о существующем методе, если он подтверждён, и оставь исполнение соответствующей самостоятельной процедуре в пределах разрешённых изменений.

## Контроль решения

Когда все известные проблемы исправлены в разрешённой копии и проверены, верни `accepted` с пустым `findings`. Когда необходимые исправления ещё не внесены — `changes_requested`; когда противоречие неразрешимо без новых данных — `needs_resolution`.

## Case вместо микроскопического Skill

**Вход:** `skills/late-load-check/SKILL.md` описывает проверку одного события `A006` по предикату `loaded_at < T` и не включает самостоятельного бизнес-результата. В `cases/` аналогичного примера нет.

**Результат:** потребуй переноса в Case с точной исторической задачей, event_id и фактической проверкой. Опубликуй Skill только когда он охватывает сквозной процесс на новых исходных данных и выпускает самостоятельный проверяемый результат. В JSON используй `changes_requested` при отсутствии прав записи; при выполненном переносе — `accepted`.
