# Подготовка самостоятельного Skill к публикации

Используй этот справочник для оформления нового или существенно изменённого Skill. Его задача — уменьшить повторную работу агента при сохранении всех проверок, необходимых для достоверности результата.

## Решение о создании

1. Установи масштаб: есть ли полноценный бизнес-процесс или сквозное преобразование сырых входов до конечного проверяемого результата?
2. Сравни с уже существующими процедурами по назначению, входам и выходу.
3. Создай Skill только для большого самостоятельного класса задач с полным процессом и результатом, если его не покрывает существующий Skill. Уточняющий приём и локальную диагностику оформляй как Case или часть подходящего большого процесса.
4. Сохрани конкретные факты прежнего решения и результаты выполненных проверок как Case; самостоятельный Skill формулируй в терминах параметров новых входов.

## Масштаб: контроль на двух входах

**Вход A:** «Почему A006 имеет два статуса на T?»; выполнена проверка двух исторических событий, получено объяснение 240 минут задержки. **Итог:** Case. Новый Skill не нужен: не восстановлен процесс от исходных данных до самостоятельного продукта.

**Вход B:** «Собери воспроизводимую сверку из нескольких CSV: импорт, срез, метрики, разбор расхождений, SQL, повторный запуск, итоговый отчёт»; все этапы реально выполнены и проверены. **Итог:** один сквозной Skill с примером схемы, данных, команд и проверенного результата.

## Рекомендуемая структура

```text
skill-name/
  SKILL.md
  references/       # необязательные подробные ветви и проверенные примеры
  scripts/          # доступный проверенный исполняемый код, если нужен
  assets/           # шаблоны, если нужны
```

```yaml
---
name: skill-name
description: "Тип самостоятельной задачи и ситуация применения."
---
```

```markdown
# Название процедуры

## Когда применять
[Триггер и результат.]

## Вход
[Данные, параметры, среда, существенные права.]

## Алгоритм
1. [Необходимое действие].
2. [Необходимое действие].

## Проверка
- [Проверка достаточности и контролируемого риска].

## Условные действия
- Если [наблюдаемое условие], [дополнительное действие].

## Результат и завершение
[Критерии правильного результата и запрошенных артефактов.]
```

Названия заголовков адаптируй к задаче. Добавляй роли, промежуточные состояния и сценарии возврата, только если от них зависит выполнение.

## Проверка границы обязательности

Для каждого действия ответь:

- Нужно ли оно для правильного результата обычного запроса из `description`?
- Если нет, какое наблюдаемое условие делает его необходимым?
- Требуется ли файл, расчёт другой версии, второй инструмент или отдельный тест пользователю либо для исключения фактического риска?
- Можно ли получить тот же корректный результат, переиспользовав доступный артефакт и проверив его применимость?

**Пример — полный процесс сверки отчётности.** При запросе построить воспроизводимый отчёт от CSV до готового результата основной путь включает верификацию входов, локальный расчёт, правильный срез, независимые денежные компоненты, объяснение остатка, SQL/способ запуска и отчёт. Если пользователь запросил только объяснение отдельного сбоя A006, используй соответствующий Case — полный процесс не запускается. Для полноценной задачи дополнительные фикстуры и вторая реализация нужны при наблюдаемом риске либо отдельном требовании.

## Мини-пример «сырой вход → результат» внутри публикуемого Skill

В полноценном Skill закрепи один проверенный демонстрационный маршрут:

```text
Вход: applications.csv (application_id, requested_amount_rub),
      decision_events.csv (application_id, status, occurred_at, loaded_at),
      payments.csv (application_id, payment_type, amount_rub, booked_at),
      T и период когорты.
Действия: проверить схему → импортировать → свести события до 1 строки на
          заявку с occurred_at<T AND loaded_at<T → рассчитать метрики →
          сверить legacy → собрать отчёт и воспроизводимый SQL.
Контроль: v1=3/8, approved amount=27000, disbursement=47000,
          refund=23000, net=24000, legacy=85000, остаток=58000.
Выход: reconciliation.sql, инструкция запуска, report.md.
```

Используй числа исключительно как контроль для этого учебного примера. Приложи реальные фрагменты SQL/кода только когда они доступны и проверены; не выдумывай вывод инструментов. Длинные исходники и расширенные ветви помещай в `references/`.

## Проверка сохранности качества

- Структура метода содержит необходимые зависимости: например, фильтр `occurred_at < T AND loaded_at < T` и документированный tie-break для исторического среза.
- Проверки исключают ошибки, существенные для результата: уникальность ключа и сохранение кардинальности после присоединения, если это необходимо.
- Потенциальный дефект не объявлен реальной причиной без измерения его вклада.
- Если основание определения неизвестно, метод требует выявить неопределённость и указать ограничение результата.
- Дополнительные примеры и файлы не являются скрытым обязательным шагом основного пути.
- В теле Skill описана только его собственная задача без ссылок на другие Skills или стадии конвейера.

## Переиспользование реализации

Исполняемый код или SQL включай в пакет, когда он уже доступен и имеет известные проверки. Укажи входные параметры, предпосылки схемы и проверяемое ожидаемое поведение. Исторический путь, не доступный в пакете, сохраняй лишь как контекст конкретного случая, без команды автоматически открыть его.

## Чтение и объём

Основной текст должен быть целостным при обычном прочтении. Большие шаблоны и специальные случаи выноси в материалы, которые читаются при необходимости. Размер контролируй по реальной читаемости, а не по универсальному лимиту строк. Заверши после прохождения необходимых проверок и подготовки результата, заданного текущим запросом.

## Пример объёма выполнения

Для вопроса «почему A006 отличается в двух отчётах?» используй существующий Case с историческими событиями. Новый Skill по такому локальному вопросу не создавай.

Для задачи «построить сверку исторической отчётности по нескольким CSV, получить показатели, объяснить остаток и выпустить воспроизводимый SQL и отчёт» используй один полноценный Skill. Основной результат: расчёты, проверки, параметризованный SQL, способ запуска и отчёт. Дополнительные фикстуры и независимые реализации применяй при выявленном риске или отдельном запросе.

Проверяй обе границы: *нужно ли вообще активировать Skill* и *какова достаточная глубина исполнения при подходящей сквозной задаче*.
