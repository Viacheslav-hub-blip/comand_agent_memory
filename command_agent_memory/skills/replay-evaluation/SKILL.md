# Сравнение результата и эффективности повторного решения

## Назначение и вход

Определи, дала ли проверяемая версия памяти подтверждённый выигрыш по качеству решения или эффективности. Сравни наблюдаемое поведение

Вход: сценарий с последовательностью сообщений пользователя, исходное и новое выполнение, ответы и файлы, трассы действий, сопоставимые измерения модели и инструментов, ограничения и настройки среды. Доступные файлы используй для оценки; не запускай заново пользовательскую задачу.

current означает свежий baseline/result с прежней памятью; candidate — свежий
result с предложенной. comparison.json фиксирует проверенный общий профиль.
Исторический reference является отдельным материалом проверки качества и не
заменяет фактические измерения свежего baseline. Незавершённый baseline может
показывать недостаток прежней памяти; candidate обязан достичь цели.

Сначала используй основные материалы, уже включённые в запрос. Дополнительную
трассу открывай для конкретного вопроса о качестве или сопоставимости; повторный
общий обход каталогов и восстановление всех отсутствующих счётчиков не нужны.
Неизвестные измерения остаются неизвестными. Вывод может опираться на другие
достаточные наблюдения: например, одинаково правильный результат и устранённое
уточнение исходного определения. При отсутствии существенных нерешённых вопросов
верни решение; полный аудит журналов не является самостоятельной целью.

## Порядок сравнения

1. **Установи сопоставимость.** Сверь исходный запрос, данные, версии, модель, инструменты, полномочия, окружение и порядок предъявления реплик. Отметь, если в одном запуске все требования находились в исходном сообщении, а в другом вводились позже. Различия, способные изменить стоимость или качество, учитывай в выводе.
2. **Проверь качество каждого ответа.** Сопоставь обязательные требования, правильность вычислений, семантику определений и версий, воспроизводимость, созданные артефакты и выполненные проверки. Рассматривай *все* сообщения, а не только финальный ответ. Прежний результат не является эталоном по умолчанию.
3. **Определи достаточный результат.** Для каждого исполнения установи, когда требуемое качество впервые достигнуто. Дополнительные отчёты, SQL-блоки, контрольные тесты и детализацию после этого считай качественным преимуществом, только если они устранили реальный риск, обязательный пробел или удовлетворили отдельное требование.
4. **Классифицируй реплики пользователя.** Раздели предотвращённое повторное объяснение, необходимое уточнение, новое требование, разрешение и формальную приёмку. Новое требование не является ошибкой памяти. Не объявляй уточнение устранённым, когда та же информация уже явно содержалась в исходных документах обоих прогонов.
5. **Измерь повторную работу.** Посчитай при наличии трасс: повторные чтения тех же материалов, пересоздание ранее пригодного решения, многократные мелкие правки одного файла, дополнительные не обусловленные запросом проверки, ошибки и повторные попытки инструментов. Выдели **преждевременные итоговые файлы** (созданы до требования и не нужны для проверки) и **файлы, необходимые для корректного выполнения**. Отдельно зафиксируй ошибки оболочки и виртуальных путей, усечение записываемого содержимого, попытки записи в память без прав и ложно успешные составные команды. Отдели использование долговременной памяти от использования контекста, созданного ранее в этом же прогоне.
6. **Сопоставь ресурсы.** Укажи отдельными величинами реальные вызовы модели, фактические вызовы инструментов, новые входные токены, кешированные входные, выходные, общие входные, время и тайм-ауты. При ограниченном охвате счётчика опирайся на трассу либо обозначай неопределённость. Не сравнивай токены с разными условиями кеширования как прямое доказательство качества памяти.
7. **Сформулируй сравнение.** Отдельно назови выигрыш по правильности, сокращению уточнений, количеству действий, токенам и времени. Укажи существенные проигрыши и внешние причины, которые невозможно отделить по данным.

## Выбор

- **`candidate`** — новая память поддерживает обязательное качество и демонстрирует убедимое преимущество: исправляет существенную ошибку, устраняет действительно ненужное уточнение либо уменьшает работу/расходы в достаточно сопоставимых условиях. Существенный проигрыш по другим показателям требует явного обоснования.
- **`current`** — прежняя версия подтверждённо даёт лучший результат или при одинаковом качестве расходует меньше ресурсов без компенсирующей пользы новой версии.
- **`inconclusive`** — недостаточны метрики, существенно различаются условия или наблюдаемые преимущества и проигрыши не позволяют обоснованно предпочесть одну версию.

Если исходные затраты отсутствуют, не заявляй выигрыш по затратам. Выбирай `candidate` без них только при независимо подтверждённом существенном качественном улучшении, которое само по себе обосновывает выбор; явно обозначь непроверенную эффективность. Больший объём результата не считается таким улучшением автоматически. При недостаточной сопоставимости не подменяй реальный эксперимент оценкой вероятной пользы.

Результат одного сравнения — локальное свидетельство, не универсальная гарантия снижения стоимости. Для причинного вывода требуется сравнение при контролируемых условиях.

## Пример: две реальные сводки → выбор по качеству и затратам

Вход — два завершённых выполнения одного сценария C01, одинаковые модель и набор четырёх реплик:

```text
                  current (без памяти)    candidate (с памятью)
Цель достигнута                да                    да
Вызовы модели                  80                   143
Вызовы инструментов            91                   155
Время рабочего агента         382 с                 510 с
Новые входные токены         230 790               555 979
Выходные токены               53 493                71 959
Проверенные результаты: v1=3/8, 27 000, выдача 47 000,
возвраты 23 000, чистая выдача 24 000 — совпали в обеих версиях.
```

Выход:

```json
{
  "choice": "current",
  "summary": "Оба запуска достигли обязательного качества при четырёх репликах. Candidate использовал 143 против 80 вызовов модели, 155 против 91 вызова инструментов, 555979 против 230790 новых входных и 71959 против 53493 выходных токенов; время рабочего агента 510 против 382 секунд. Подтверждённого качественного преимущества, компенсирующего перерасход, нет. Для данного сопоставления предпочтителен current; причинный вывод о памяти в целом требует повторов."
}
```

Другой случай: baseline не завершён, candidate объяснил подтверждённую существенную ошибку — оцени улучшение качества отдельно. При отсутствии исходных метрик и недоказанной сравнительной корректности верни `inconclusive`. Не объявляй более длинный отчёт автоматическим выигрышем.

## Формат результата

Верни **ровно один JSON без Markdown** и дополнительных полей:

```json
{
  "choice": "candidate | current | inconclusive",
  "summary": "Качество каждого результата, число и тип уточнений, повторная работа, числовые затраты, сопоставимость, ограничения и причина решения"
}
```

Не изменяй файлы; прекрати анализ, когда достаточные для решения свидетельства уже получены. Не выполняй исходную задачу повторно и не создавай вспомогательные проекты или длинные отчёты ради сравнения.
