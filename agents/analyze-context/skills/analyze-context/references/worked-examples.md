# Few-shot примеры анализа контекста

Примеры показывают требуемый уровень обобщения. В отчёте нет отдельного раздела проектного контекста. Определения появляются только из объяснения пользователя.

## Пример 1. Выбор провайдера обобщается без деталей исправления

### История

1. Пользователь: «У меня нет `TYPESAFE_API_KEY`, я не хочу использовать TypeSafe, я хочу использовать только OpenRouter».
2. Агент перестраивает пример и перечисляет удалённые SDK, переменные и эндпоинты.
3. Пользователь продолжает эксперименты с несколькими моделями через OpenRouter.

### Выход

```markdown
## Предпочтения
- Для подключения к моделям пользователь предпочитает провайдер OpenRouter.
```

### Почему так

Будущему агенту нужен выбор провайдера. Перечень удалённых переменных, SDK и конкретный идентификатор модели описывают одну реализацию и не расширяют предпочтение.

---

## Пример 2. Частный файл обобщается до типа проверки

### История

1. Пользователь описывает проблему: агент вызывает инструмент до того, как собрал достаточно информации, и придумывает параметры.
2. Пользователь предлагает дополнительную проверку: хватает ли данных из запроса пользователя для вызова инструмента.
3. В созданном примере эта проверка реализована в `example_2.py` через Jev и последний запрос пользователя.

### Выход

```markdown
## Инструкции и ограничения
- Перед вызовом инструмента проверять, что необходимые аргументы получены от пользователя, а не придуманы агентом или подставлены из значения по умолчанию.
```

### Почему так

`example_2.py`, Jev и форма передачи последнего сообщения относятся к реализации примера. Сохраняется цель проверки, пригодная для других инструментов и моделей.

---

## Пример 3. Structured output без имени файла и модели

### История

1. Пользователь: «Давай будем просить DeepSeek вернуть structured output `{"answer": ""}`, а не tool call».
2. Агент изменяет функцию в `example_3.py` и применяет JSON Schema.

### Выход

```markdown
## Предпочтения
- Для структурированного ответа пользователь предпочитает JSON Schema вместо представления результата через tool call.
```

### Почему так

Пользователь выбрал способ получения структурированного результата. Имя файла, конкретная модель и поле демонстрационного объекта не нужны для применения выбора в похожей задаче.

---

## Пример 4. Требование текущего примера не становится постоянной памятью

### История

1. Агент предлагает переписать демонстрацию без middleware.
2. Пользователь: «Middleware нужно оставить».
3. Агент возвращает middleware в текущий файл.

### Выход

```text
Сведений для обновления памяти не обнаружено.
```

### Почему так

Пользователь исправил структуру одной демонстрации. Он не установил правило использовать middleware во всех будущих задачах.

---

## Пример 5. Запрет изменять пользовательские данные становится правилом

### История

1. Агент удаляет ключ из пользовательского `config.py`.
2. Пользователь: «Я хочу, чтобы ключ оставался в файле config. Ты не имеешь права удалять то, что написано мной».

### Выход

```markdown
## Инструкции и ограничения
- Не удалять и не заменять написанные пользователем данные без его явного разрешения.
```

### Почему так

Смысл исправления шире расположения одного ключа: пользователь прямо задаёт границу полномочий агента. Название файла не нужно для применения правила.

---

## Пример 6. Термины, объяснённые агентом, не становятся определениями

### История

1. Пользователь просит провести эксперимент с Jev, Laya и DeepSeek.
2. Агент объясняет понятия `Jev`, `is_risky`, `has_enough_data`, «окно контекста» и формат меток Laya.
3. Пользователь просит изменить код и сравнить результаты, но сам не объясняет значения этих терминов.

### Выход

```text
Сведений для обновления памяти не обнаружено.
```

### Почему так

Упоминание термина пользователем и объяснение агента не подтверждают пользовательское определение. Технические сведения из кода и ответов агента также не создают словарные записи.

---

## Пример 7. Условие одного эксперимента не становится определением

### История

1. Пользователь: «Сравним результаты с DeepSeek, считаем его эталоном».
2. Агент выполняет один тест и рассчитывает процент совпадений.

### Выход

```text
Сведений для обновления памяти не обнаружено.
```

### Почему так

DeepSeek назначен эталоном одного сравнения. Пользователь не дал определение термина и не установил общее правило для будущих экспериментов.

---

## Пример 8. Пользователь сам определяет показатель

### История

1. Пользователь: «В этом отчёте конверсия — число оплаченных заказов, делённое на число созданных заказов. Отменённые заказы остаются в знаменателе».
2. Агент строит расчёт по этой формуле.

### Выход

```markdown
## Определения и предметные правила
- **Конверсия** (этот тип отчёта): число оплаченных заказов, делённое на число созданных заказов; отменённые заказы входят в знаменатель.
```

### Почему так

Пользователь сам объяснил показатель, формулу и исключение. Агент только применил уже заданный смысл.

---

## Пример 9. Промежуточные результаты большой задачи

### История

1. Пользователь поручает длительную переработку презентации.
2. Агент долго работает без показа результата.
3. Пользователь просит показывать промежуточные варианты, чтобы видеть ход большой задачи.

### Выход

```markdown
## Предпочтения
- При работе над большой задачей пользователь предпочитает получать промежуточные результаты по мере готовности.
```

### Почему так

Из частного случая извлечена потребность, применимая к большим задачам. Вывод «скорость важнее качества» не добавляется, потому что пользователь этого не говорил.
