# Сквозные примеры консолидации

Все примеры учебные. Их цель — показать, как преобразовать **новый отчёт и старую память** в конкретное изменение разрешённых файлов. Имена систем и результаты служат только для иллюстрации способа обработки. Каждый пример содержит исходные сведения, целевые фрагменты и объяснение решения.

## Пример 1. Несколько исправлений формируют одно предпочтение

### Исходные материалы

**Прежний `USER_PREFERENCES.md`:**

```markdown
# Предпочтения
- При подготовке больших документов предпочитает получать итог одним файлом.
```

**Новый отчёт:**

1. Пользователь просит: «Покажи уже готовые разделы, пока работаешь над остальными».
2. После завершения очередного раздела уточняет: «Это удобно; в больших задачах присылай законченные части по мере готовности».
3. Позже добавляет: «Итоговый файл в конце тоже нужен».

### Итоговый `USER_PREFERENCES.md`

```markdown
# Предпочтения
- При работе над большими задачами показывать готовые части по мере завершения; в конце предоставлять единый итоговый результат.
```

### Логика консолидации

Предпочтение охватывает способ взаимодействия при больших задачах. Новая просьба уточняет порядок представления результата, сохраняя потребность в итоговом файле. Объедини смысл в одной записи. Утверждение о том, что пользователь ценит скорость выше качества, материалы не подтверждают.

### Пограничный случай

Если пользователь говорил только «этот раздел пришли сейчас», запись остаётся условием конкретного поручения до появления основания для дальнейшего применения.

## Пример 2. Разовая правка оформления не становится предпочтением

### Исходные материалы

**Прежняя память:** `USER_PREFERENCES.md` содержит «Для рабочих Excel предпочитает простое оформление таблиц».

**Новый отчёт:**

- Пользователь: «В этой таблице P1–P8 убери цветные заливки, но оставь ширину столбцов, границы и перенос строк».
- Пользователь позднее: «Для всех таблиц с антифрод-правилами используй нейтральную заливку; структуру ячеек сохраняй».

### Итоговое изменение

Новой записи в `USER_PREFERENCES.md` нет. Условие относится к конкретным
таблицам антифрод-правил. Его можно сохранить в статье соответствующего проекта,
если оно понадобится при следующей работе с ним.

### Логика консолидации

Последняя просьба задаёт область «все таблицы с антифрод-правилами», а не разные
проекты пользователя. Имена P1–P8 показывают исходный пример, но не являются
параметрами будущего требования.

### Пограничный случай

Общее предпочтение можно добавить только после указания пользователя, что оно
применимо к разным задачам или проектам.

## Пример 3. Одно сообщение содержит инструкцию и факты о системе

### Исходные материалы

**`AGENTS.md` до консолидации:**

```markdown
# Работа с проектами
- Изменения архитектуры агента согласовывать с пользователем.
```

**`user_llm_wiki/pages/atlas.md` до консолидации:**

```markdown
# Atlas
- Проект на Python.
```

**Новый отчёт:**

Пользователь: «В Atlas логи читаются из SQLite и Codex. Для настройки памяти меняем только `AGENTS.md`, `USER_PREFERENCES.md` и Skills. Системный промпт и код основного агента оставляем без изменений. Подключение Claude Code планируется позже».

### Изменение `user_llm_wiki/pages/atlas.md`

```markdown
# Atlas
- Проект на Python.
- Источники истории: диалоги из SQLite и логи Codex.
- Планируется адаптер для Claude Code.
- Для настройки памяти в этом проекте изменяются только `AGENTS.md`, `USER_PREFERENCES.md` и Skills; системный промпт, код и внутренняя архитектура агента не меняются.
```

### Логика консолидации

Раздели исходный текст по назначению. Ограничения на настройку относятся к Atlas,
поэтому остаются в его статье wiki. Доступные источники логов и план адаптера —
также проектный контекст. Общее правило о согласовании архитектуры можно оставить
в `AGENTS.md` только без привязки к Atlas.

### Пограничный случай

Если список разрешённых файлов установлен только для конкретного эксперимента,
не сохраняй его в постоянной памяти.

## Пример 4. Бизнес-формула требует другой консолидации

### Исходные материалы

**Новый отчёт:**

```markdown
## Определения и предметные правила
- В отчёте D «чистая выдача» = выданные суммы − возвраты, комиссии в формулу не входят.

## Личный и проектный контекст
- Отчёт D строится в системе Atlas Finance.
```

**Прежняя личная wiki:** сведений об Atlas Finance нет.

### Итоговая личная память

`user_llm_wiki/pages/atlas-finance.md`:

```markdown
# Atlas Finance
- Система используется для построения отчёта D.
```

`INDEX.md`:

```markdown
- [Atlas Finance](pages/atlas-finance.md) — система подготовки отчёта D.
```

### Итоговое сообщение консолидации

«Для консолидации предметных знаний: термин “чистая выдача” в отчёте D = выданные суммы − возвраты; комиссии не входят в формулу. Основание — пользовательское определение, переданное в отчёте».

### Логика консолидации

Формула содержит предметную семантику и должна попасть в каталог определений на другом этапе. Текущий Skill обновляет лишь контекст системы Atlas Finance. Знак вычитания, состав показателя и исключение комиссий передаются точно.

### Пограничный случай

Если в личной wiki уже обнаружено определение, подготовь сообщение о необходимости переноса в предметные знания и сохрани доступное свидетельство до выполнения переноса.

## Пример 5. План переходит в частично реализованное состояние

### Исходные материалы

**Прежняя wiki:**

```markdown
# Система обработки логов
- Планируется загрузка событий из Phoenix.
```

**Новый отчёт с данными теста:**

«Инструмент успешно прочитал из Phoenix 100 событий типа `tool_call`. События типа `message` ещё не проверялись. Пользователь подтвердил, что это тест адаптера, промышленное включение планируется отдельно».

### Итоговая wiki

```markdown
# Система обработки логов
- Адаптер Phoenix: тестовое чтение 100 событий типа `tool_call` выполнено успешно.
- Поддержка событий `message` ещё требует проверки.
- Промышленное включение адаптера запланировано отдельно.
```

### Логика консолидации

Обнови состояние только проверенного участка. Сохрани границы теста, тип событий и статус внедрения. Число 100 показывает масштаб фактической проверки; оно не задаёт постоянного лимита системы.

### Пограничный случай

Если инструмент завершился без данных о корректности содержания, формулируй наблюдение как технический результат чтения; качество извлечения требует отдельного подтверждения.

## Пример 6. Пользователь явно заменяет прежнее правило

### Исходные материалы

**Новый отчёт:**

Пользователь: «Обнови наше правило для Iris: финальные исследовательские отчёты теперь сохраняем в HTML. Markdown оставим для промежуточных заметок».

### Итог

Новой записи в `AGENTS.md` нет. Форматы относятся к Iris и могут быть обновлены
только в статье этого проекта, если она нужна для продолжения работы.

### Логика консолидации

Исправление задаёт новую редакцию в области Iris. Сохрани два формата с их
назначением в контексте Iris, не превращая проектное условие в общее правило.

### Пограничный случай

Если пользователь попросил HTML только для одного отчёта, не создавай запись.

## Пример 7. Два противоречащих предпочтения без подтверждённого исправления

### Исходные материалы

**Прежний `USER_PREFERENCES.md`:**

```markdown
- Для технических обзоров предпочитает краткий вывод перед подробным разбором.
```

**Новый отчёт:**

«Пользователь в ответ на один обзор попросил сначала полный технический разбор, а затем вывод. Указаний о постоянном изменении предпочтения нет».

### Итоговая память

Сохрани прежнюю запись. В итоговом сообщении поясни, что единичная просьба относилась к конкретному обзору и не задаёт общего изменения.

### Пограничный случай: реальный конфликт

Если новый отчёт утверждает «для всех технических обзоров сначала полный разбор», но отсутствует исходная история и ясное отношение к прежнему предпочтению, оставь текущую запись и передай ревьюеру формулировки обеих сторон. При явном «замени прежнее правило» обнови запись.

### Логика консолидации

Различай локальную вариацию выдачи и новое постоянное предпочтение. Частота, дата или уверенная формулировка анализатора сами по себе не доказывают отмену прежнего требования.

## Пример 8. Устранение смыслового дубля между AGENTS.md и предпочтениями

### Исходные материалы

**Прежний `AGENTS.md`:**

```markdown
- Пользователь любит, когда финансовые показатели объясняются простыми словами.
- Перед изменением схемы базы данных согласовывать изменение с пользователем.
```

**Прежний `USER_PREFERENCES.md`:**

```markdown
- При обсуждении финансовых показателей предпочитает практические объяснения.
```

**Новый отчёт:**

«При ответах по финансовым метрикам сначала объясняй практический смысл каждого показателя».

### Итоговый `USER_PREFERENCES.md`

```markdown
- При объяснении финансовых показателей сначала раскрывать их практический смысл простым языком.
```

### Итоговый `AGENTS.md`

```markdown
- Перед изменением схемы базы данных согласовывать изменение с пользователем.
```

### Логика консолидации

Две записи об объяснении показателей выражают одну потребность пользователя. Сведи её в раздел предпочтений; отдельно сохрани общее правило о согласовании. Новый отчёт уточняет порядок объяснения метрики.

### Пограничный случай

Если пользователь требует от агента определённую формулу расчёта финансового показателя, такой смысл относится к предметным правилам или проектным инструкциям в зависимости от происхождения и назначения.

## Пример 9. Переменная численность датасета и две версии данных

### Исходные материалы

**Прежняя wiki:**

```markdown
# Данные проекта Vector
- Выборка содержит около 12 млн событий.
```

**Новый отчёт:**

«После добавления периода 2026-09 подготовлена версия V2, содержащая около 19 млн событий. Версия V1 с 12 млн строк продолжает использоваться для сравнения моделей».

### Итоговая wiki

```markdown
# Данные проекта Vector
- Версия V1: около 12 млн событий; используется для сравнения моделей.
- Версия V2: около 19 млн событий после добавления периода 2026-09.
```

### Логика консолидации

Сохрани оба числа, поскольку обе версии продолжают использоваться. Укажи соответствующие им наборы и назначение; это помогает выбрать правильный датасет в следующей задаче.

### Пограничный случай

Если V1 полностью выведена из использования и её параметры уже не нужны для воспроизводимости, достаточно актуального описания V2 с нужной датой.

## Пример 10. Создание страницы и индекса по новой теме

### Исходные материалы

**Прежний `user_llm_wiki/INDEX.md`:**

```markdown
# Личная wiki
- [Рабочая среда](pages/environment.md) — устройства и инструменты.
```

**Новый отчёт:**

«Пользователь разрабатывает `GraphLens`: сервис анализа журналов вызовов инструментов. Он хранит события в SQLite, предоставляет HTML-представление выполненных прогонов и планирует интеграцию с Phoenix. В текущем состоянии чтение Phoenix ещё не реализовано».

### Созданная `pages/graphlens.md`

```markdown
# GraphLens

## Назначение
Сервис анализа журналов вызовов инструментов ИИ-агентов.

## Реализовано
- Хранение событий в SQLite.
- HTML-просмотр выполненных прогонов.

## Планы
- Интеграция с Phoenix.
```

### Обновлённый `INDEX.md`

```markdown
# Личная wiki
- [Рабочая среда](pages/environment.md) — устройства и инструменты.
- [GraphLens](pages/graphlens.md) — анализ журналов агентов, хранилище, интерфейс и планы интеграции.
```

### Логика консолидации

Новая самостоятельная тема получает страницу. Индекс отражает назначение и позволяет следующему агенту найти сведения. Реализованные компоненты и планы разделены.

### Пограничный случай

Если новый факт относится к уже существующей странице о GraphLens, дополни её. Выбирай число страниц по смысловой структуре тем.

## Пример 11. Агент предложил определение, пользователь подтвердил другой аспект

### Исходные материалы

**Новый отчёт:**

1. Агент: «Назовём активным клиента, у которого было три входа за семь дней. Сохраню файл в HTML».
2. Пользователь: «HTML подходит. Сделай файл».
3. Инструмент сохранил отчёт и подтвердил его наличие.

### Итоговая личная память

Из этого фрагмента не требуется новая постоянная запись, если формат HTML относится только к данному отчёту. Выдуманное определение «активного клиента» не передавай как утверждённое.

### Итоговое сообщение

«Новых сведений для персональной памяти нет. Бизнес-определение “активного клиента” из предложения агента не имеет явного подтверждения пользователя; при необходимости требуется уточнение».

### Логика консолидации

Согласие на формат и подтверждение сохранения файла относятся к выполненному поручению. Они не устанавливают значение бизнес-термина.

### Пограничный случай

При ответе «Да, определение активного клиента верно, используй его в следующих отчётах» передай точный смысл определения в консолидацию знаний.

## Пример 12. Конфиденциальность при обновлении проектного контекста

### Исходные материалы

**Прежняя wiki:** «Сервис использует интеграцию с внутренним API».

**Новый отчёт:** «Сервис обращается к `/events`; в логе напечатаны рабочий токен, имя сотрудника и идентификатор сессии. Для поиска ошибок достаточно знать, что используется `SESSION_ID`».

### Итоговая wiki

```markdown
# Интеграция сервиса
- Для событий используется конечная точка `/events`.
- Для связывания операций в журнале используется `SESSION_ID`.
```

### Логика консолидации

Имена интерфейса и переменной сохраняют технический смысл. Для понимания архитектуры достаточно названий интерфейса и переменной; значения токена и идентификаторы прогона опусти.

### Пограничный случай

Если существующий файл памяти уже содержит токен, удали его значение в разрешённой копии и сообщи о необходимости устранить его раскрытие в исходных системах через предусмотренный процесс, не повторяя секрет.

## Пример 13. Нулевое изменение — полноценный результат

### Исходные материалы

**Прежний `USER_PREFERENCES.md`:**

```markdown
- В технических ответах предпочитает русский язык и минимальное количество англицизмов.
```

**Новый отчёт:**

```markdown
## Предпочтения
- В технических обсуждениях предпочитает русский язык с меньшим количеством англицизмов.
```

### Итог

Файл остаётся без изменений. В ответе: «Проверено одно предпочтение; существующая запись полностью покрывает новое утверждение. Изменённых файлов нет».

### Логика консолидации

Две формулировки выражают один смысл с одинаковой областью. Переписывание не приносит новой информации.

### Пограничный случай

Если новый отчёт добавляет «имена классов и функций оставлять английскими», внеси уточнение рядом с прежним предпочтением.

## Пример 14. Исправление ошибочной категоризации без потери знания

### Исходные материалы

**Прежний `AGENTS.md`:**

```markdown
- Система Signal использует `GigaChat-3-Ultra` для текстовой аналитики.
- Перед включением внешних API согласовывать интеграцию с пользователем.
```

**Новый отчёт:**

«В рабочем прототипе Signal модель `GigaChat-3-Ultra` используется для анализа сообщений. Режим промышленного исполнения ещё обсуждается».

### Итоговый `AGENTS.md`

```markdown
- Перед включением внешних API согласовывать интеграцию с пользователем.
```

### Итоговая `user_llm_wiki/pages/signal.md`

```markdown
# Signal
- В рабочем прототипе для анализа сообщений используется `GigaChat-3-Ultra`.
- Режим промышленного исполнения находится на обсуждении.
```

### Логика консолидации

Перемести факт о технологии в контекст проекта. Уточни доказанный этап «прототип» и статус будущего внедрения. Сохрани общее правило о согласовании API в `AGENTS.md`.

### Пограничный случай

При отсутствии разрешения редактировать существующий `AGENTS.md` выполни доступную часть изменений и отметь необходимый перенос для дальнейшего этапа.

## Пример 15. Уточнение старого факта без полного переписывания страницы

### Исходные материалы

**Прежняя wiki:**

```markdown
# Конвейер памяти

## Назначение
Фоновый анализ истории работы агентов.

## Архитектура
- Анализатор извлекает новые сведения.
- Консолидация обновляет память.
- Ревьюер проверяет результат.

## Реализовано
- Поддержка логов Codex.
```

**Новый отчёт:**

## Пример 16. Личный контекст и ошибочное расширение предпочтения

### Исходные материалы

**Прежняя wiki:** «Пользователь готовит исследовательскую работу об архитектуре ИИ-агентов».

**Новый отчёт:**

1. Пользователь: «Для этой работы нужно пять разделов и краткий текст выступления».
2. Пользователь: «В будущем хочу продолжить исследования по агентной памяти».
3. Агент: «Значит, пользователь всегда предпочитает пять разделов и короткие выступления».

### Итоговая wiki

```markdown
- Пользователь готовит исследовательскую работу об архитектуре ИИ-агентов и планирует продолжить исследования агентной памяти.
```

### Итог `USER_PREFERENCES.md`

Новая постоянная запись не требуется.

### Логика консолидации

Структура одного выступления определяет локальную задачу. Намерение продолжать исследования является будущим направлением работы. Общее предпочтение устанавливай на основании указания пользователя.

### Пограничный случай

Если пользователь затем явно скажет «для всех моих докладов придерживайся пяти разделов», появится основание для отдельного предпочтения или инструкции в обозначенной области.
