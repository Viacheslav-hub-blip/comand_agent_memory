# Примеры проверки согласованности объединения памяти

Примеры показывают отношения между прежней памятью, новыми основаниями и
предложенной копией. Основания конкретного запуска берутся из его материалов.

## 1. Разные условия одного правила

Прежняя память: для проекта А отчётные суммы хранятся в рублях.
Новое основание: в проекте Б суммы выражены в копейках.
Предложенная копия: «Все суммы выражены в копейках».

Правка: сохранить правило проекта А и добавить отдельное правило проекта Б.
Причина: объединение расширило область нового сведения и потеряло прежнее.

```json
{"decision":"accepted","summary":"Восстановлены отдельные области проектов А и Б; прежнее правило сохранено, новое относится к своему проекту.","findings":[]}
```

## 2. Явная замена правила

Прежняя память: заказчик получает отчёт раз в месяц.
Новое основание: пользователь явно установил еженедельную отправку для того же
отчёта с указанной даты.
Предложенная копия: старое расписание заменено новым, дата перехода сохранена.

Действие: принять уточнение. Исторический период и область нового расписания
сохранены; замена подтверждена указанием пользователя.

```json
{"decision":"accepted","summary":"Новое расписание относится к тому же отчёту и подтверждено явным изменением пользователя; дата перехода сохранена.","findings":[]}
```

## 3. Конфликт при совпадающих условиях

Прежняя память: у показателя определён один знаменатель.
Новый отчёт: для того же показателя, периода и версии указан другой знаменатель.
Доступные материалы оставляют вопрос об отмене прежнего определения открытым.

Действие: зафиксировать обе позиции, совпадающие условия и требуемый источник
разрешения. Выбор формулы требует подтверждения владельца определения.

```json
{"decision":"needs_resolution","summary":"При одинаковых показателе, периоде и версии обнаружены несовместимые определения знаменателя.","findings":[{"file":"wiki/metric.md","problem":"Прежняя и предложенная записи задают разные знаменатели для одного показателя в одинаковых условиях; основание замены отсутствует.","change":"Получить подтверждение определения и даты его действия у владельца показателя."}]}
```

## 4. Историческая проверка получила статус постоянного требования

Материалы: в прошлой задаче агент сравнил число строк и число различных сущностей;
получено 6 и 6. Новый Case сохранил этот результат, но распространил проверку
на каждый будущий запуск как обязательную.

Правка: сохранить обобщённую ситуацию, конкретный эпизод и результат 6/6.
Постоянную обязательность заменить условиями аналогии, подтверждёнными источником.
Причина правки — расширение области действия вывода при объединении.

```json
{"decision":"accepted","summary":"Сохранён конкретный опыт проверки 6/6; область переноса привязана к сходству условий исходного эпизода.","findings":[]}
```

## 5. Крупный Case и отсутствие Skill-кандидата

Материалы раскрывают сложное единичное расследование. Консолидатор сохранил Case
с обобщённой ситуацией и подробным конкретным решением. Описание воспроизводимого
агентом бизнес-процесса в материалах отсутствует.

Действие: принять Case при согласованности с прежними сведениями. Размер эпизода
характеризует прошлую задачу. Основание для Skill проверяется по описанию процесса.

```json
{"decision":"accepted","summary":"Подробный Case сохраняет конкретный прошлый опыт и его условия; предложение согласуется с прежней памятью.","findings":[]}
```

## 6. Потерянное исключение

Прежняя память: правило действует при условии Х, а для условия Y предусмотрено
отдельное исключение. Новый материал дополнил основной способ работы.
При объединении исключение исчезло, хотя основания отмены отсутствуют.

Правка: восстановить исключение и сохранить дополнение в его подтверждённой области.

```json
{"decision":"accepted","summary":"Восстановлено подтверждённое исключение для условия Y; новое дополнение сохранено для условия Х.","findings":[]}
```

## Формат ответа

Верни один JSON-объект. Выполненные правки и их основания укажи в summary;
findings содержит оставшиеся проблемы согласованности. Для accepted верни
пустой findings.
