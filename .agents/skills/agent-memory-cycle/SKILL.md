# Обновление памяти самостоятельными скиллами

Ты управляешь этапами в текущем агентном клиенте. В установленном комплекте восемь
скиллов этапов лежат рядом с этим каталогом. В checkout их исходники находятся в
`command_agent_memory/skills/`. На каждом смысловом этапе вызывай свежую штатную
агентную сессию с инструментами чтения и соответствующим SKILL.md. Укажи её
конкретные входы, допустимую рабочую область и ожидаемый выход. Сохраняй полный
результат с ID сессии в журнале. При невозможности запустить независимый этап
сообщи, какой исполнитель недоступен.

Технические команды ниже вызывает ведущий агент. `io` означает
`python -B -X utf8 <абсолютный путь к scripts/memory_io.py>`. Нужен Python 3.11+.
Команда выполняет одну операцию ввода-вывода и возвращает JSON. Модель и
инструменты предоставляет клиент. Не запускай `run_memory.py` или модуль конвейера.

1. Используй явно заданный JSON подключений, затем `memory_pipeline.json` в
   корне рабочего проекта. Для последнего диалога без конфига вызови
   `io discover --project <каталог> --host codex|claude`; для экспорта добавь
   `--source jsonl --history <путь>`. Сохрани возвращённый JSON во временный файл.
   Если источник не найден, предложи настройку через `agent-memory-setup`.
   Учитывай `wishes_file` в заданиях этапов. Если пользователь
   запросил только проверку, выполни `io check --config C` и верни результат.
   Добавляй `--replay` к check и prepare, если он запрошен.
2. После общей проверки для каждого участника выполни `io prepare --config C --user U`.
   Получишь путь R, список сессий, каталог `R/history`, исходный снимок `R/before`
   и рабочую копию `R/draft`. Статус no_sessions завершает цикл этого участника.
   Если известен стабильный идентификатор модели и инструментов, передай его в prepare
   через `--profile`. При reused используй возвращённый принятый запуск для команды.
   Журналы содержат историю пользователя. Для собственного workspace используй
   локальную область вне отслеживаемых файлов Git.
3. Для **каждой** сессии отдельно вызови **context-analysis** и **procedure-analysis**.
   Дай каждому путь к полному экспорту данной сессии. Длинные файлы читай диапазонами
   до конца. Сохрани оба отчёта в R под именами с номером сессии.
4. Если настроен personal, поручай **personal-memory-consolidation** отчёты контекста
   и личные пути в draft. Если настроен knowledge, поручай **knowledge-consolidation**
   отчёты обоих видов и только пути знаний в draft. Передай `memory_layout` из JSON
   подготовки. Сохрани diff и перечитай изменённые документы.
5. Вызови независимый **memory-review**. Передай оба вида отчётов, before, draft,
   перечень изменений и границы. Исправления допустимы только в draft. Запиши
   финальное решение в `R/review.json`. В `R/stages.json` запиши объект с ключами
   `context-000001`, `procedures-000001` для каждой сессии с её номером,
   `consolidation` и `knowledge` для настроенных областей и `review`. Значение
   каждого ключа содержит фактический `session_id` исполнителя и `report` —
   относительный путь к его полному ответу внутри R (разделитель /). Для review
   используй `review.json`. При отказе сообщи причину и закончи личный
   цикл. При accepted без замечаний выполни `io seal --config C --user U --run R`.
6. Для запрошенного replay следуй [протоколу сравнения](references/replay.md).
   Затем выполни `io publish --config C --user U --run R`. При устаревшем снимке
   требуется новый цикл с актуальным before. Ошибка одного участника сохраняется
   в его результате; продолжай обработку остальных участников.
7. Для настроенной команды обработай принятые вклады и доставку по
   [протоколу командной памяти](references/team.md). Верни по участникам состояние,
   решение ревью и replay, путь к status.json, для Git также SHA доставленного снимка.
