# Командный реестр знаний

Реестр реализован 5 ноября 2026 года. Функций и классов в документе нет.
Команда запуска и JSON-конфигурация сохраняются: `team.root` задаёт хранилище,
`team.workspaces` — получателей принятой памяти.

## Состав хранилища

```text
shared-memory/
  INDEX.md
  wiki/
  cases/
  skills/
  .registry/state.json
```

`.registry/state.json` содержит `version: 1`, словарь `sources` и словарь `entries`.
У каждой записи — устойчивый ID и список `versions`. Версия содержит:

| Поле | Назначение |
| --- | --- |
| `revision`, `run_id` | Номер версии знания и создавший её запуск |
| `status` | `accepted`, `pending` или `conflicts` |
| `statement`, `conditions` | Утверждение и известные условия применения |
| `reason` | Основание принятия, ожидания или спора |
| `evidence_ids` | Ссылки на проверенные личные документы в `sources` |
| `conflicts_with` | ID несовместимых записей; только для `conflicts` |
| `documents` | Полные документы версии, закодированные в base64 без потери байтов |

Источники содержат владельца, область памяти, исходные сессии, путь, SHA-256
и исходные байты личного документа, принятые запуски и их статус replay. ID источника не зависит
от повторного запуска и replay. Одинаковый документ из того же набора сессий
не создаёт новое подтверждение при повторной обработке. Изменение документа
может создать новую версию источника, но его сессии сохраняются: оно само по себе
не доказывает независимость. Независимость помечена `not_established` до смысловой
проверки; числового счётчика независимых подтверждений нет.

## Обновление

1. Проверяются статус и хеши принятых личных снимков.
2. Консолидатор читает реестр, историю решений, проверенные источники и документы.
3. В одном сеансе он возвращает JSON с `decision`, `summary`, `findings`, `updates`.
   Формат записей и правила сопоставления заданы в
   `command_agent_memory/skills/team-memory-consolidation/SKILL.md`.
   Парсер допускает пояснение и Markdown вокруг JSON, проверяя точную схему
   внешнего решения. JSON внутри документов не подменяет внешнее решение.
4. Python проверяет источники, состояния, пути и взаимные ссылки конфликтов.
5. Приложение строит действующие документы только из `accepted` и создаёт INDEX.md
   со ссылками на них. Реестр и действующая память публикуются одним файловым
   обновлением с общей проверкой исходного снимка и откатом при ошибке.

Файловая публикация по-прежнему не является атомарной для стороннего читателя;
обновление и доставку запускают между задачами агента. Модельный консолидатор
файлы не пишет. Для OpenRouter задаётся пустая область записи и отключается shell;
для Codex используется read-only sandbox. Пользовательские адаптеры должны
соблюдать тот же контракт.

Смысловую достаточность оснований оценивает консолидатор с обязательным `reason`.
Числовой порог допуска не назначен. Replay проверяет применение знания и сам
по себе не подтверждает истинность утверждения. Разные корректные определения
с разными условиями могут одновременно оставаться `accepted`.

При настоящем конфликте обе стороны получают `conflicts`; прежде принятая
сторона обновляется под прежним ID. Ссылки должны быть взаимными. Бесспорные
знания остаются действующими. При частичном споре консолидатор выделяет спорную
часть в самостоятельный документ: один активный документ принадлежит одной записи.

`pending` и `conflicts` передаются консолидатору на следующих обновлениях.
Для перехода в `accepted` нужны дополнительный source-ID и объяснение нового
содержательного основания. Это структурная проверка нового основания, а не
доказательство его независимости: смысл проверяет LLM. При разрешении конфликта
обновляются все связанные стороны. Неподтверждённая сторона может остаться pending.
Одинаковое решение не добавляет версию только из-за другого ID запуска.

Отказ консолидатора, неизвестный источник, повреждённый JSON, некорректный переход,
изменение входного личного снимка или ошибка публикации сохраняют действующую
память и прежний реестр. В журнале запуска остаются материалы и доступное решение.

## Совместимость и доставка

При первом обновлении прежние документы сохраняются как `legacy-*` записи
со статусом `accepted`, без выдуманных источников. Их байты и бинарные приложения
сохраняются; прежний INDEX.md заменяется индексом приложения. Неизменные записи
не требуется включать в ответ модели. Бинарное приложение старой версии нельзя
перезаписать текстом LLM; при обновлении записи оно сохраняется автоматически.
Новые документы в `updates` передаются как UTF-8-тексты либо как
`{"source_id": "ID основания этой записи"}` для точного копирования принятого
документа, включая бинарное приложение. Исходные байты хранятся в реестре;
base64 не включается в контекст модели.

Получатель получает только текущие accepted-документы и индекс. Реестр, архивные
версии, кандидаты и спорные записи не копируются в `team_knowledge/`. Ранее
доставленное спорное знание удаляется из управляемой копии при следующей доставке.
Изменение файлов действующей памяти вне реестра обнаруживается и останавливает
следующее обновление или доставку до восстановления согласованного снимка.

Git-транспорт этим изменением не добавлен. Реестр сохраняет происхождение на
уровне принятых документов и исходных сессий; он не доказывает автоматически,
что утверждение не было ранее скопировано из командной памяти. Консолидатор
должен учитывать известное происхождение и сохранять неизвестность при его нехватке.

## Версии инструкций

StageRuntime включает содержимое всех встроенных `SKILL.md` и файлов `references/`
в отпечаток конфигурации. Изменение, добавление или удаление ресурса отменяет
повторное использование ранее принятого результата. Это консервативная стратегия:
изменение любого встроенного skill может повторно запустить также другие этапы.
Хеши сохраняются в `configuration/skills.json`. Изменение инструкций во время
запуска останавливает обработку вместо сохранения неверной версии настроек.
