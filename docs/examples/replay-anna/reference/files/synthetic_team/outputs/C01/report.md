# C01 — сверка заявочных и денежных величин (метод + результат)

Определение: **v1** (архивное, опубликовано 2026-10-01; тестовые заявки входят).
Срез знания: **2026-10-03 00:00:00 UTC**, верхняя граница не включается.
Когорта: `created_at` в [2026-10-01 00:00:00, 2026-10-03 00:00:00).
Источник: локальная SQLite, собранная по `sql/schema.sql`; CSV загружены стандартным Python. Исходные файлы не изменялись.

> Числа ниже — иллюстрация метода на текущей когорте. Тот же SQL воспроизводит сверку
> для другой когорты через параметры `--cohort-lo/--cohort-hi/--as-of/--definition`;
> в текст запросов даты и суммы не зашиты.

## Вывод

Старый запрос даёт `approved_amount_rub = 85 000` по 6 строкам, но это не сопоставимо с денежными величинами и не равно корректной сумме одобренных на срез. Причины: берётся любое `approved`-событие вместо последнего известного статуса, и не учитывается время появления записи в хранилище (`loaded_at`). Размножение заявок при JOIN в этом снимке вклада не даёт.

## Показатели на срез T

| Показатель | Значение |
|---|---|
| Заявок в когорте | 8 (7 реальных + 1 тестовая) |
| Одобрено на срез (v1) | 3 (A001, A004, A005) |
| Сумма `requested_amount_rub` по одобренным | 27 000 |
| Выдача (disbursement, `booked_at < T`) | 47 000 |
| Возвраты (refund, `booked_at < T`) | 23 000 |
| Чистая выдача (выдача − возвраты) | 24 000 |
| approval_rate v1 | 3 / 8 = 0.375 |

Заявочные и денежные величины не обязаны совпадать: «одобрение» — решение по заявке, «выдача» — движение денег; `requested_amount_rub` — запрошенная сумма, не факт перечисления. Основания времени разные: когорта по `created_at`, решения по `occurred_at`, деньги по `booked_at`.

| # | Причина | Заявки | Вклад |
|---|---|---|---|

## Метод сверки (воспроизводимо, повторно применимо)

Пять этапов; каждому соответствует блок в `reconciliation.sql`.

### 1. Определения и периоды
Фиксируем: что считаем «одобрением» (решение, а не деньги), границы когорты по `created_at` (нижняя включена, верхняя нет), дату среза знания T, версию определения (v1/v2) и обработку тестовых заявок. Тесты показываем отдельной величиной, чтобы включение было видимым.
→ `01_definitions_periods`.

### 1b. Проверка версии определения и режима воспроизведения
Версия (v1/v2) и правило тестовых заявок **выводятся из параметра**, а не предполагаются; отдельно фиксируется режим — `historical_reproduction` (знание на T: `occurred_at < T AND loaded_at < T`). Контроль режима: показываем, сколько строк отсекает фильтр `loaded_at` (были бы видны при фильтрации только по `occurred_at`). Пересчёт прошлого с учётом поздних событий — другой режим, его нельзя смешивать с историческим воспроизведением.
→ `01b_definition_version_and_mode`.

### 2. Гранулярность
`applications` : `decision_events` — один-ко-многим. Перед любой заявочной метрикой проверяем, не размножается ли заявка при соединении и не даёт ли она больше одного `approved`-события.
→ `02_granularity_check`, `03_granularity_summary`.

### 3. Приведение истории к согласованному срезу
Сначала оставляем `occurred_at < T AND loaded_at < T` (поздняя загрузка не переписывает прошлое знание), затем берём первую строку в порядке `occurred_at DESC, event_id DESC`. Результат — ровно одна строка на заявку.
→ `04_decision_snapshot`.

### 4. Сравнение компонент
Считаем раздельно и сопоставляем: одобренные заявки на срез и сумму по ним (`requested_amount`), approval_rate (числитель/знаменатель/период/срез/версия), справочно `final_decision_approval_rate`, и денежные компоненты (выдача, возвраты, чистая выдача по `booked_at < T`).
→ `05_approved_on_snapshot`, `06_approval_rate`, `07_final_decision_approval_rate`, `08_money_components`.

### 5. Объяснение остатка
Воспроизводим старый запрос как есть, затем раскладываем разницу по корзинам без зашитых сумм:
`in_both`, `legacy_extra_status` (статус на срез иной или поздняя загрузка), `legacy_extra_test`, `snapshot_only` (аномалия).
→ `09_legacy_query_as_is`, `10_residual_decomposition`, `11_residual_totals`.

## Как повторить для другой когорты

```
python run_reconciliation.py \
  --cohort-lo "2026-09-01 00:00:00" --cohort-hi "2026-10-01 00:00:00" \
  --as-of "2026-10-03 00:00:00" --definition v1
```

Раннер создаёт локальную базу по `schema.sql`, загружает CSV из `inputs/` и выполняет
блоки SQL с параметрами `:cohort_lo, :cohort_hi, :as_of, :include_test`.
Меняются только аргументы; текст `reconciliation.sql` остаётся тем же.
