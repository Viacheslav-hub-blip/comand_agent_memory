# C02. Борис: воспроизводимый срез истории

Оператору: user_id=102, новый сеанс. Сценарная дата 4 октября. Данные исторического среза не меняются вслед за датой разговора.

## Реплика 1

```text
Я Борис, инженер данных команды «Север». В рабочих SQL предпочитаю именованные CTE и явный список колонок. Если понадобится Python для обработки данных, обычно использую pandas, но ничего не устанавливай: без него здесь достаточно csv и sqlite3. Проверь /synthetic_team/sql/legacy_approval.sql по /synthetic_team/documents/data_dictionary.md. Нужен воспроизводимый запрос: одна строка на заявку, состояние, известное на 2026-10-03 00:00:00 UTC, когорта регистраций за 1–2 октября. Начни с проверки ключей и объяснения того, что сломано в старом запросе.
```

## Реплика 2

```text
История решения — это поток событий, а не справочник с одной строкой на заявку. Для меня «срез знания» означает состояние, которое мы могли увидеть в хранилище к указанному моменту. A006 специально оставлена с поздней загрузкой, а у A007 два события с одинаковым бизнес-временем. Посмотри в документации, как выбирать между ними; не выбирай запись по алфавиту статуса.
```

## Реплика 3

```text
Сделай два результата для сравнения: исторически известное состояние и пересчёт на то же бизнес-время с учётом всех уже загруженных поздних событий из снимка. Для второго режима фильтруй occurred_at по прежней границе, но loaded_at не ограничивай. Покажи только заявки, по которым результаты отличаются. Выполни запросы в локальном SQLite на CSV и сохрани их в /synthetic_team/outputs/C02/. Исходники не меняй.
```

В завершение добавь проверки уникальности application_id после выбора среза и сохранения числа заявок при LEFT JOIN.
