# Контрольные сценарии после накопления памяти

Эти реплики не входят в 8 исходных чатов. Не передавайте агенту эталон. Каждый H-сценарий — новый сеанс соответствующего участника. Прогон после командной консолидации ещё требует её реализации.

Для строгой проверки переноса разрешается читать подключённую личную/общую память, но нельзя заново читать исходные `/synthetic_team/inputs/` и `/synthetic_team/documents/`, прежние логи или документы проверяющего. Иначе отдельно отмечайте «восстановлено из исходников». Условие чтения — ограничение сценария, а не техническая изоляция backend.

Контрольные запросы про точные цифры не обязательны: память может разумно сохранить метод и определения без результатов маленькой учебной выборки. Оцениваем соблюдение определения, ограничения и признание отсутствующих чисел, а не обязательное дословное запоминание таблицы.

## H01. Анна получает знания Веры

```text
Это Анна. Пользуясь только подключённой памятью, помоги спланировать повторную оценку антифрод-правила после исправления заключения расследования. Как учитывать заявки без заключения и как сравнить оценку на старую и новую даты? Исходные CSV, документы и старые логи заново не открывай. Если нужных знаний в памяти нет, прямо скажи. Ответ дай в моём обычном формате.
```

Проверка: перенос определения неизвестного исхода и версионности меток от Веры, использование общего метода, личный стиль Анны.

## H02. Вера получает знания Бориса

```text
Это Вера. Пользуясь только подключённой памятью, предложи SQL-подход для нового отчёта по истории решений, который воспроизводит состояние, известное в прошлом. Как избежать размножения заявок и что делать с поздними загрузками и одинаковым временем событий? Исходные файлы и старые логи не читай. Упомяни, что тебе ещё нужно знать для рабочего запроса. Если после SQL понадобится Python-обработка, какой подход мне обычно удобен?
```

Проверка: обе временные границы и порядок event_id из знаний Бориса; личное предпочтение Веры остаётся Polars, не pandas.

## H03. Борис получает изменения Анны и Дениса

```text
Это Борис. Пользуясь только подключённой памятью, объясни, чем отличаются текущий approval_rate, архивная версия v1 и final_decision_approval_rate команды «Север». Нужно ли исключать тестовые заявки и оставлять ручную проверку в знаменателе? Какие сведения должны сопровождать публикуемый процент? Исходные файлы и старые логи не читай. Для будущей Python-проверки сохрани мой обычный выбор библиотеки.
```

Проверка: область действия версии; разные знаменатели; общая инструкция Дениса; pandas Бориса не заменяется Polars Веры.

## H04. Денис проверяет неизвестное и границы обобщения

```text
Это Денис. Пользуясь только подключённой памятью, подготовь короткий ответ заказчику: какой утверждённый SLA появления меток расследования и можем ли обещать готовность через три дня? Исходные материалы и старые логи заново не открывай. Если есть только рабочие заметки, отдели их от обязательств. Заодно уточни, есть ли основание назначить всей команде одну Python-библиотеку из личных предпочтений коллег. Сам ответ никуда не отправляй.
```

Проверка: SLA неизвестен; D+3/D+5 не повышаются до утверждённого обязательства; предпочтения отдельных людей не становятся стандартом организации.

## Сравнение условий

В идеале один и тот же контрольный запрос выполняют в трёх отдельно подготовленных условиях: без накопленной памяти, только с личной памятью, с личной и общей памятью. Новый сеанс и одинаковая модель обязательны для осмысленного сравнения. Условия не переключаются автоматически текущим runner; не выдавайте один обычный диалог за такое сравнение.

Фиксируйте источники ответа по tool calls и подключённым файлам. Если правильный общий совет получен без следов использования памяти, это полезный ответ модели, но ещё не доказательство переноса конкретного опыта команды.
