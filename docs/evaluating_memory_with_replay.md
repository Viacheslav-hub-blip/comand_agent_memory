# Проверка памяти штатным рабочим агентом

Проверка выполняется как часть конвейера:

```powershell
python -m command_agent_memory --config memory_pipeline.json --evaluate-by-replay
```

Укажите `replay_scenario` у пользователя. Модели тестировщика и оценщика выбираются
через `stages.replay_tester` и `stages.evaluation` либо defaults. Рабочий агент
задаётся отдельно полем `agent` сценария и не наследует модель анализа памяти.
Прежнее поле stages.replay_agent удалено: перенесите подключение в agent.factory/options.

## Сценарий и штатная фабрика

```json
{
  "messages": ["Проверь расхождение отчёта", "Сохрани результат в report.md"],
  "goal": "Объяснить расхождение и сохранить проверенный отчёт",
  "inputs": "inputs",
  "reference": "reference",
  "agent": {
    "factory": "command_agent_memory.working_agent:create_session",
    "options": {
      "model": "YOUR_WORKER_MODEL_ID",
      "model_parameters": {"temperature": 0},
      "run_config": {"recursion_limit": 120, "max_concurrency": 2}
    }
  }
}
```

Замените модель на модель рабочего агента. Встроенная фабрика собирает локальный
DeepAgents с теми же файловыми и shell-инструментами, что и обычная функция
`command_agent_memory.working_agent.create_agent`. Параметры, системные инструкции
и дополнительные tools должны совпадать с рабочим запуском. Проект со своими
SQL/API/MCP-инструментами указывает собственную штатную фабрику, возвращающую
WorkerSession. Контракт описан в [руководстве по интеграциям](adding_integrations.md).
model_parameters задаёт параметры генерации; run_config сохраняет штатные лимиты
графа и параллелизма. Используйте значения своего рабочего приложения.

Никакой обязательной контейнерной среды нет. Локальные команды работают с правами
пользователя. Независимые копии файлов не являются песочницей ОС. Фабрика проекта
сама подготавливает подключения, программы и отдельные состояния внешних ресурсов;
она не должна случайно привязать оба опыта к одной изменяемой рабочей базе.

`inputs` содержит исходные файлы, `reference/answer.md` — исторический ответ для
проверки качества. Материалы должны находиться в допустимой области конфигурации;
inputs и reference раздельны. Исходные реплики должны использовать пути, которые
штатные инструменты фабрики связывают с копией задачи. Произвольные абсолютные пути
из старого чата автоматически не переназначаются.

Вместо messages можно задать dialogue_source — Markdown с репликами в блоках text.
Если request задан, он совпадает с первой репликой. reference_metrics хранит
исторические измерения; они не заменяют измерения нового baseline.

## Два независимых запуска

1. Из before и after создаются две копии с одинаковыми входными файлами.
2. Одна фабрика создаёт два новых экземпляра рабочего агента.
3. До модельных вызовов сравниваются модель и её параметры, хеш инструкций,
   фактические имена/схемы/реализации tools и описание среды. Профили сохраняются.
4. Первый экземпляр решает задачу с прежней памятью; второй — с предложенной.
   Внутри каждого диалога сохраняются один экземпляр и один thread_id, включая
   результаты инструментов и штатное состояние. Ограничения графа не подменяются.
5. Ресурсы обеих фабрик освобождаются через cleanup также при ошибках.
6. Оценщик сравнивает результаты и реальные измерения двух свежих запусков.

Рабочему агенту передаются только пользовательские реплики. Тестировщик получает
цель, исходные реплики и исторический reference; он выбирает следующие реплики по
возрастающим индексам либо подтверждает цель. Первое наблюдение включает
initial_context с фактической памятью и входами. Reference не включается в запросы
исполнителя и не копируется в его рабочую область. Доступ через произвольный shell
при этом ограничивается правами исходного агента, а не отдельной изоляцией проверки.

Профиль не должен содержать секреты, абсолютный путь конкретной копии или содержимое
памяти. Снимки внешних ресурсов описываются в environment. Это контракт доверенной
фабрики: журнал диалога автоматически не восстанавливает её код и подключения.
Если фабрика отсутствует, tools/среда различаются либо общий экземпляр используется
в двух запусках, проверка завершается ошибкой настройки без публикации памяти.

## Принятие и журналы

При нехватке самого сценария, реплик, входов или исторического ответа сохраняется
skipped; память принимается по ревью по прежнему правилу. Если полный сценарий есть,
отсутствие agent является ошибкой, а не основанием перейти к упрощённому агенту.

Candidate должен завершить цель. Незавершённый baseline может быть наблюдаемым
недостатком прежней памяти. Технический сбой, изменение проверяемой памяти или
несопоставимость условий останавливают публикацию. Входы внутри копии могут штатно
изменяться инструментами задачи; исходные inputs не изменяются самим конвейером.
Права инструментов не заменяются запретами replay. Проверка неизменности памяти
выполняется после хода, не является блокировкой ОС и не ограничивает shell.

Публикация разрешена только при выборе candidate. Выбор current или inconclusive
сохраняет действующую память. Неизвестные измерения остаются null. Польза одного
сравнения не считается универсальным доказательством экономии.

Материалы в consolidation-runs/<ID>/personal/replay/:

```text
agent-profile.json       профиль штатного агента
comparison.json          общий отпечаток и хеши исходных входов
baseline/workspace/      копия с прежней памятью
baseline/result/         ответ, трасса, метрики и файлы baseline
workspace/               копия с предложенной памятью
result/                  ответ, трасса, метрики и файлы candidate
reference/               исторические материалы качества
evaluation/              запрос и ответ оценщика
decision.json            выбор версии памяти
```
