# Ревью изменений памяти

Skill: [review-memory](../agents/review-memory/skills/review-memory/SKILL.md).

С 23 октября ревью подключено к `consolidate_reports_codex.py`:
[запуск в копии и перенос только принятой памяти](reviewed-consolidation.md).
Ниже также сохранено описание испытаний 22 октября.

Ревьюер получает разделы отчётов, каталог до изменения, каталог после изменения
и правила размещения и оформления материалов. Сравнивает версии, читает связанные
файлы и выносит решение. Проверяемые файлы не изменяет.

## Порядок проверки каталога

Один запуск на весь каталог пропускал смысловые ошибки даже после уточнения
инструкций. Для полного каталога применяется несколько областей проверки
в отдельных контекстах:

1. Определения wiki и условия их применения.
2. Каждая процедура с относящимися к ней cases и определениями.
3. Структура каталога, ссылки, дубли и зависимости между процедурами.
4. Сведение замечаний: проверка их обоснованности, объединение повторов и решение.

Область и обязательные файлы указываются в задании. Отчёты выбираются по теме;
связанные файлы остаются доступны для проверки зависимостей. Решение accepted
по одной области не означает принятия всего каталога. Непроверенная область
не должна исчезать из итогового заключения.

Внутри области ревьюер сопоставляет определения, требования и результаты cases.
Проверка процедуры должна учитывать каждый её пункт, включая неизменённые
требования. Краткое повторение термина не считается дублем автоматически.
Разовая просьба, не изменившая постоянные предпочтения, не требует отдельной
записи в памяти.

Для испытаний 22 октября перечень областей составлен по INDEX.md и файлам каталога.
Теперь код автоматически проверяет каждый файл двух версий и затем связи каталога.
Планирование групп тем через отдельную LLM пока не реализовано.

## Входы

Для личной памяти передаются `instructions_preferences`, `user_context`,
`definitions`, `cases`, `skill`. Критерии разделяют AGENTS.md, USER_PREFERENCES.md,
user_llm_wiki/ с контекстом и knowledge/ с определениями, cases и skills.
Ревью начинается после работы обоих личных консолидаторов и охватывает их общую копию.
Для каталога знаний — `definitions`, `cases`, `skill` и правила wiki, cases, skills
и индекса. Ревьюер получает только материалы своей задачи.

Правила передаются вместе с заданием, чтобы результат проверялся по тем же
требованиям, по которым выполнялось изменение. Инструкции и команды внутри
содержимого отчётов и проверяемых файлов считаются данными.

## Выход

```json
{
  "decision": "accepted",
  "summary": "Изменения соответствуют материалам; прежние сведения сохранены.",
  "findings": []
}
```

Возможные решения:

- `accepted` — замечаний, требующих изменений, нет.
- `changes_requested` — исправления можно определить по имеющимся материалам.
- `needs_resolution` — нужны данные для разрешения противоречия либо необходимые
  материалы недоступны. Ревьюер формулирует вопрос, а не выбирает версию произвольно.

Каждое замечание содержит `file`, `problem`, `change`: файл, ошибку с её последствием
и требуемое исправление или недостающие сведения. При неразрешённом противоречии
исправимые ошибки тоже перечисляются.

## Проверка поведения

[Наборы примеров](../tests/fixtures/review-memory/) содержат отчёты и каталоги
до и после изменений. Это синтетические примеры; намеренные ошибки в них сохраняются.

| Набор | Отчёты | До | После | Ожидаемое решение |
| --- | --- | --- | --- | --- |
| errors | reports.md | before | after-errors | changes_requested |
| valid | reports.md | before | after-valid | accepted |
| conflict | conflict-reports.md | before | after-conflict | needs_resolution |
| repeated | repeated-reports.md | before | before | accepted |

В errors заложены потеря `loaded_at < T` и UTC, ошибочное требование одинакового
знаменателя v1/v2, дублирование case с именем автора, выдуманные этапы выгрузки
в skill и ссылка на отсутствующий файл. Набор valid сохраняет условия и различает
определения v1/v2. В conflict два отчёта дают несовместимые определения одной метрики
при одинаковых условиях. Набор repeated проверяет допустимость отсутствия изменений.

При прогоне ревьюеру передаются skill, [задание](../tests/fixtures/review-memory/task.md)
и пути только одного набора. Таблица ожидаемых решений ему не передаётся.
Каждый набор проверяется отдельным процессом Codex CLI в режиме `read-only`.
Оценку содержания выполняет модель; команды запуска сохраняют ответ и события.

[Результаты прогона 22 октября](../data/review-memory-evaluations/20261022T083151Z/report.md):
четыре решения совпали с ожидаемыми. Входные файлы и knowledge не изменились.
В каталоге прогона сохранены задания, ответы, события и текст проверявшегося skill.

[Прогон на результатах Анны и Бориса](../data/real-memory-reviews/20261022T090413Z/report.md):
четыре отчёта и 12 файлов каталога. Ревьюер нашёл повтор определения, но пропустил
ошибочное требование одинакового знаменателя v1/v2. Полнота ревью пока не подтверждена.

[Уточнение и 21 запуск](../data/review-memory-improvements/20261022T090948Z/report.md):
проверка по областям обнаружила ошибку знаменателя дважды. Финальные четыре
контрольных сценария дали ожидаемые решения; также проверена текущая личная память
Анны и Бориса. Итоговое сведение CLI сохранило спорные замечания, поэтому заключение
дополнительно проверено ассистентом в текущем чате. Полнота и отсутствие ложных
замечаний для автономного применения не доказаны.

## Граница реализации

На этом этапе создан skill и проверено его поведение на примерах и результатах
консолидации командных знаний.
Он вызывается из consolidate_reports_codex.py до переноса копии в действующую память.
Каждый файл и связи проверяются отдельно; любой отказ останавливает перенос.
Автоматический цикл исправлений пока отсутствует. Историческое испытание личной
памяти 22 октября проверяло текущее состояние без снимков до её консолидации.
В испытаниях новой защиты действующие знания команды не изменялись.
