# Система накопления личной и командной памяти ИИ-помощников

## Для чего нужен этот документ

Документ описывает проект в его текущем состоянии. Он предназначен для обсуждения
с руководителем перед подготовкой материалов для научной конференции.

Здесь собраны:

- проблема, которую решает проект;
- предлагаемое решение;
- практическая польза;
- устройство системы;
- движение данных от строки чата до памяти команды;
- назначение файлов проекта;
- результаты проведённых опытов;
- ограничения текущей версии;
- план развития;
- возможная научная постановка.

## Краткое описание

Рабочие диалоги сотрудников с ИИ-помощниками содержат полезные сведения:
предпочтения пользователя, правила работы, определения показателей, причины
ошибок, удачные способы решения и полные процессы выполнения больших задач.

После завершения чата эти сведения обычно остаются внутри истории. Другой
помощник, новый сотрудник и сама команда используют их только после повторного
объяснения.

Проект превращает историю диалогов в управляемую память. Система сохраняет
исходные сообщения, делает два независимых смысловых разбора, готовит изменения
в отдельной копии памяти, проводит проверку всей копии, выполняет контрольную
задачу и только после успешных проверок публикует новую версию памяти.

Память разделена на личную и командную. Личная память помогает учитывать правила,
предпочтения и контекст одного сотрудника. Командная память хранит общие
определения, карточки опыта и полные процессы решения больших задач.

## Проблема

### Знания остаются в чатах

В рабочем диалоге сотрудник может объяснить:

- смысл показателя;
- причину расхождения в отчёте;
- правило выбора исторического состояния;
- способ проверки соединения таблиц;
- порядок подготовки итогового отчёта;
- ограничение, связанное с данными или процессом.

История хранит эти сведения как последовательность сообщений. Для повторного
использования человеку приходится искать нужный разговор и заново восстанавливать
контекст.

### Личные и командные сведения смешиваются

Одна реплика может одновременно содержать предпочтение сотрудника, проектный факт,
предметное определение и часть общего рабочего процесса. Простое сохранение всей
реплики в общую память приводит к смешению областей применения.

Пример:

- просьба показывать короткий вывод перед таблицей относится к предпочтениям;
- название конкретного поля относится к локальной схеме проекта;
- правило исторического среза относится к предметным знаниям;
- полная сверка показателей относится к процессу большой задачи.

### Ошибочное обобщение создаёт риск

Единичный удачный запрос может выглядеть как общий метод. Локальное имя таблицы
может попасть в процесс, который затем применят к другому проекту. Предположение
модели может превратиться в определение. Старое правило может противоречить новой
версии показателя.

Поэтому памяти требуется отдельная проверка происхождения, области действия,
версий и связей между материалами.

### Объём памяти влияет на работу помощника

Большой набор инструкций и справочных материалов способен увеличить число
обращений к модели и инструментам. Проведённые опыты показали, что расход зависит
главным образом от траектории выполнения задачи. Размер файлов памяти играет
меньшую роль.

Для управляемой работы требуется точное разделение:

- справочник хранит определения;
- карточка опыта хранит один механизм;
- описание процесса хранит большую задачу целиком;
- техническая среда отвечает за пути, запуск команд и измерения.

### Командной памяти требуется доверие

Общее знание влияет на нескольких сотрудников. Публикация должна учитывать:

- источник сведения;
- область применения;
- подтверждение несколькими участниками;
- различия версий;
- спорные утверждения;
- возможность восстановления предыдущего состояния.

Текущая версия уже создаёт копии, проверку и резервные снимки. Реестр происхождения
каждого пункта и порядок командного подтверждения входят в следующий этап.

## Предлагаемое решение

Система обрабатывает диалоги последовательными этапами.

1. Сохраняет каждое сообщение пользователя, помощника и инструмента.
2. Выгружает один диалог в читаемый построчный файл.
3. Выполняет разбор контекста пользователя.
4. Выполняет разбор опыта и полных процессов.
5. Объединяет результаты с действующей памятью в рабочей копии.
6. Проверяет всю копию отдельным проверяющим помощником.
7. При наличии сценария решает контрольную задачу с новой памятью.
8. Сравнивает новый результат с прежним.
9. Публикует принятую копию и сохраняет прежнее состояние.

Каждый этап оставляет файлы, журналы и измерения. Это позволяет разбирать сбои,
сравнивать варианты и повторять обработку с нужного места.

## Как устроена память

### Личная память

Личная память находится внутри рабочей области пользователя.

| Место | Содержание |
|---|---|
| `AGENTS.md` | Общие полномочия и постоянные правила работы |
| `USER_PREFERENCES.md` | Устойчивые предпочтения общения и оформления |
| `user_llm_wiki/` | Контекст пользователя, проектов и систем |
| `knowledge/` | Предметные знания и процессы, связанные с личным опытом пользователя |
| `skills/` | Ранее созданные локальные процессы рабочей области |

### Командная память

Командная память находится в корневом каталоге `knowledge/`.

| Тип | Русское пояснение | Содержание |
|---|---|---|
| `wiki/` | Справочник | Термины, формулы, версии и предметные правила |
| `cases/` | Карточки опыта | Отдельная проблема, причина, приём, проверка и эффект |
| `skills/` | Полные процессы | Решение большой задачи от входа до принятого результата |
| `INDEX.md` | Оглавление | Ссылки и условия выбора материалов |

Текущий командный каталог содержит 3 статьи справочника, 16 карточек опыта и
3 полных процесса.

## Основные принципы

### Разделение ответственности

Каждый факт хранится в одном основном месте. Остальные материалы используют
ссылки. Такое устройство сокращает повторения и облегчает обновление версий.

### Работа через копию

Консолидатор и проверяющий помощник изменяют отдельную рабочую копию. Действующая
память сохраняется до принятия результата.

### Проверка всей области

Проверяющий помощник получает прежнюю память, предложение, полные отчёты и правила
размещения. Он исправляет копию и возвращает решение строгой структуры.

### Контрольная задача

Повторный прогон показывает, помогает ли новая память решить реальную задачу.
Решающий помощник получает чистый контекст, копию входных данных и выбранный
вариант памяти. Прежний ответ хранится отдельно и используется только оценщиком.

### Восстановление после сбоя

Каждый запуск хранит исходный снимок, предложение, версию после проверки,
журналы модели и состояние этапов. Для остановившихся проверок существуют
отдельные команды продолжения.

### Измеримость

Система сохраняет время, число обращений, вызовы инструментов и данные об объёме
сообщений модели. Эти сведения нужны для сравнения качества и стоимости.

## Архитектура

```text
История чата
    |
    v
SQLite или журнал Codex
    |
    v
Построчная история JSONL
    |
    +-------------------------+
    |                         |
    v                         v
Разбор контекста        Разбор опыта и процессов
    |                         |
    +------------+------------+
                 |
                 v
       Полные отчёты по чатам
                 |
                 v
       Консолидация в копии
                 |
                 v
       Проверка и исправление
                 |
                 v
       Контрольная задача
                 |
                 v
       Сравнение результатов
                 |
                 v
       Публикация памяти
```

### Уровень вызова моделей

Проект поддерживает два способа вызова модели:

- Codex через командную программу;
- OpenRouter через программный интерфейс.

Новый пакет `command_agent_memory/adapters/` задаёт единый договор вызова.
Анализ использует режим одного ответа. Консолидация и контрольная задача используют
помощника с доступом к файлам и командной строке.

### Уровень запусков

`command_agent_memory/runs/` создаёт уникальные каталоги. Существующий каталог
сохраняет прежние результаты. Каждый запуск получает сортируемый идентификатор,
содержащий дату, время и случайную часть.

### Уровень синтетических диалогов

`command_agent_memory/synthetic/` читает сценарии независимо от выбранной модели.
Исполнитель получает уже проверенный список участников, сообщений и источников.

### Уровень памяти

`reviewed_consolidation.py` управляет снимками, блокировкой, рабочей копией,
проверкой и публикацией. Для личного этапа он запускает два консолидатора над одной
копией:

1. консолидатор правил, предпочтений и личного контекста;
2. консолидатор предметных знаний, карточек опыта и полных процессов.

### Уровень повторной проверки

`replay_evaluation.py` подготавливает копию новой памяти и входных данных,
запускает одну задачу, сохраняет результат и передаёт его оценщику. Оценщик
выбирает новую память, прежний вариант или состояние недостаточной определённости.

## Полный путь одной строки чата

Ниже описан путь каждой записи. Он одинаков для пользовательской реплики, ответа
помощника и сообщения инструмента.

### Шаг 1. Появление сообщения

Пользователь отправляет реплику. В синтетическом опыте текст берётся из одного
блока `text` файла `docs/examples/synthetic-team/chats/*.md`.

`run_synthetic_dialogues.py` передаёт текст в `run_turn()`.

### Шаг 2. Немедленная запись пользовательской строки

`agent_runtime.run_turn()` создаёт сообщение пользователя и вызывает
`save_message()` до обращения к модели.

В таблицу `messages` записываются:

| Поле | Значение |
|---|---|
| `id` | Порядковый номер строки |
| `session_id` | Идентификатор диалога |
| `user_id` | Идентификатор сотрудника |
| `created_at` | Время записи в UTC |
| `role` | Роль: пользователь, помощник или инструмент |
| `content` | Читаемый текст |
| `message_json` | Полное сообщение модели с вызовами инструментов и измерениями |

После вставки выполняется фиксация изменений базы. Поэтому уже полученные строки
сохраняются при последующем сбое.

### Шаг 3. Работа решающего помощника

`create_agent()` собирает новый экземпляр помощника. Он получает:

- модель из `settings.py`;
- рабочую область пользователя;
- `AGENTS.md`;
- `USER_PREFERENCES.md`;
- доступные оглавления личного справочника и знаний;
- локальные процессы из `skills/` и `knowledge/skills/`;
- отдельное хранилище состояния текущего диалога.

Одинаковый `session_id` продолжает разговор. Другой идентификатор создаёт чистый
контекст.

### Шаг 4. Запись ответов и инструментов

Помощник возвращает поток событий. `run_turn()` проходит по каждому событию.
Каждое сообщение помощника и каждый результат инструмента передаются в
`save_message()` и становятся отдельной строкой SQLite.

В итоге одна пользовательская реплика создаёт несколько строк:

```text
human -> ai с вызовом инструмента -> tool -> ai -> tool -> ai с итоговым ответом
```

Точное число строк зависит от хода решения.

### Шаг 5. Выбор диалога для анализа

`analyze_chats_codex.py` получает список `session_id` выбранного пользователя.
Для SQLite выполняется группировка строк по сеансу и сортировка по первому `id`.
Для журналов Codex список формирует `codex_history.list_sessions()`.

### Шаг 6. Выгрузка в JSONL

`memory_pipeline.export_chat_history()` открывает SQLite в режиме чтения и
выполняет запрос:

```sql
SELECT id, role, content, message_json
FROM messages
WHERE user_id = ? AND session_id = ?
ORDER BY id
```

Каждая строка базы превращается в одну строку файла JSONL:

```json
{
  "id": 17,
  "role": "user",
  "message": {
    "type": "human",
    "data": {
      "content": "текст сообщения"
    }
  }
}
```

Поле `content` добавляется отдельно при расхождении с полным сообщением.
Порядок строк сохраняется по `id`.

### Шаг 7. Два смысловых разбора

Для каждого диалога выполняются два отдельных задания модели.

`analyze-context` извлекает:

- общие правила пользователя;
- устойчивые предпочтения;
- личный и проектный контекст;
- подтверждённые определения.

`analyze-procedures` извлекает:

- карточки отдельных проблем;
- причины и проверенные приёмы;
- полный процесс большой задачи при наличии всех стадий.

При OpenRouter полная JSONL-история включается в инструкцию модели. При Codex
модель получает путь к файлу и читает его целиком.

Результаты сохраняются в:

```text
session-<идентификатор>/context.md
session-<идентификатор>/procedures.md
session-<идентификатор>/manifest.json
```

`manifest.json` отмечает состояние, завершённые виды разбора, модель, источник и
пути к файлам.

### Шаг 8. Сбор отчётов пользователя

`memory_pipeline.read_reports()` обходит каталоги `session-*`. Для завершённого
диалога он читает `context.md` и `procedures.md` целиком. Тексты нескольких
диалогов соединяются через пустые строки.

Контекстные отчёты идут в личную консолидацию. Оба вида отчётов идут в
консолидацию знаний.

### Шаг 9. Создание снимка

`reviewed_consolidation.read_memory()` читает действующую память как набор:

```text
относительный путь -> байты файла
```

Система создаёт:

- `before/` с исходным состоянием;
- `workspace/memory/` с рабочей копией;
- `materials.md` с полными отчётами;
- `rules.md` с правилами консолидации;
- отдельные инструкции и журналы каждого консолидатора.

### Шаг 10. Личная консолидация

Первый консолидатор обновляет в рабочей копии:

- `AGENTS.md`;
- `USER_PREFERENCES.md`;
- `user_llm_wiki/`.

Он распределяет сведения по смыслу и объединяет их с существующими записями.

### Шаг 11. Консолидация знаний пользователя

Второй консолидатор читает контекстные и процедурные отчёты. Он обновляет
`knowledge/` внутри той же рабочей копии:

- определения и локальную предметную схему в `wiki/`;
- отдельные механизмы в `cases/`;
- полные процессы больших задач в `skills/`;
- ссылки в `INDEX.md`.

### Шаг 12. Проверка и исправление

Отдельный проверяющий помощник получает:

- прежний снимок;
- предложение до проверки;
- изменяемую копию;
- все исходные отчёты;
- правила размещения;
- примеры проверки.

Он проверяет всю область, исправляет копию и возвращает один объект JSON с полями:

```json
{
  "decision": "accepted",
  "summary": "описание проверки",
  "findings": []
}
```

Парсер принимает только объект заданной структуры. Итоговая копия сохраняется в
`after/`.

### Шаг 13. Контрольный повтор задачи

При включённой проверке система создаёт `replay/workspace/`. Туда копируются:

- принятая проверяющим память;
- чистые входные данные сценария;
- доступные локальные процессы.

Прежний ответ находится в `replay/reference/` и остаётся за пределами рабочей
области решающего помощника.

Новый помощник получает чистый идентификатор диалога и решает задачу. Система
сохраняет ответ, созданные файлы, историю действий и измерения.

### Шаг 14. Сравнение

Оценщик получает запрос, входы, прежний результат, новый результат, журналы и
измерения. Его решение содержит:

- `candidate`, если новая память дала предпочтительный результат;
- `current`, если действующая память остаётся предпочтительной;
- `inconclusive`, если материалов для выбора мало.

Публикация после выполненного контрольного прогона требует выбора `candidate`.

### Шаг 15. Публикация личной памяти

Перед публикацией система повторно читает действующую память и сравнивает её с
исходным снимком. Это защищает от параллельного изменения.

Новая версия сначала записывается в `publish/`. Действующие каталоги перемещаются
в `backup/`, затем новая версия занимает целевое место. При исключении система
возвращает сохранённые элементы.

### Шаг 16. Попадание в память команды

Командный этап получает отчёты нескольких сотрудников. В проведённом опыте
отчёты Бориса и Веры были собраны в общий каталог с именами `session-*`.

`read_reports()` читает все пары `context.md` и `procedures.md`. Их полный текст
становится материалом этапа `knowledge`. Консолидатор обновляет корневой каталог
`knowledge/`, проверяющий исправляет общую копию, после чего принятая версия
публикуется как память команды.

## Прослеживаемость строки

До этапа смыслового анализа путь строки прослеживается точно:

```text
messages.id
 -> JSONL.id
 -> файл истории конкретного session_id
 -> журнал задания анализа
```

После анализа модель объединяет несколько строк в свободный текст отчёта.
Формальная связь между исходным `message_id` и конкретным пунктом справочника,
карточкой опыта или полным процессом сейчас отсутствует. Связь восстанавливается вручную через каталог запуска,
историю и отчёты.

Для следующей версии предлагается реестр происхождения:

```text
fact_id
user_id
session_id
message_ids
hash исходного фрагмента
тип памяти
целевой файл
статус проверки
подтверждения участников
версия публикации
```

Такой реестр даст машинную цепочку от пункта командной памяти до исходных реплик.

## Практическая выгода

### Для сотрудника

- помощник учитывает устойчивые предпочтения;
- проектный контекст сохраняется между задачами;
- повторные объяснения сокращаются;
- проверенные процессы доступны в следующей работе;
- прежние решения можно воспроизвести по журналам.

### Для команды

- опыт разных сотрудников собирается в едином каталоге;
- определения и версии показателей становятся видимыми;
- типовые ошибки оформляются как карточки опыта;
- большие задачи получают полные повторяемые процессы;
- новый сотрудник получает доступ к проверенному способу работы.

### Для руководителя

- появляется карта знаний команды;
- видны пробелы, конфликты и спорные определения;
- можно оценивать стоимость применения памяти;
- история публикаций позволяет разбирать происхождение решений;
- контрольные задачи дают практическую оценку полезности.

### Для организации

- рабочие знания меньше зависят от одного человека;
- обучение новых сотрудников опирается на реальные задачи;
- единые определения снижают расхождения отчётности;
- накопленный опыт становится основой для внутренних помощников;
- сравнение вариантов памяти помогает управлять затратами моделей.

## Масштабируемость

### Новые средства вызова модели

`command_agent_memory/adapters/` содержит общий договор. Новый способ вызова
добавляется через отдельный адаптер. Анализ и консолидация используют единый
объект с режимом одиночного ответа и режимом работы с инструментами.

### Новые источники диалогов

Сейчас доступны SQLite и журналы Codex. Новый источник должен вернуть ту же
построчную историю с ролями и порядком сообщений. После этого вся последующая
цепочка остаётся общей.

### Новые участники

Каждый сотрудник получает отдельную рабочую область и базу сообщений. Командная
консолидация принимает отчёты нескольких областей.

### Новые предметные области

Справочники содержат локальные термины и поля. Карточки опыта описывают отдельные
механизмы. Полные процессы используют смысловые роли данных. Благодаря этому
один процесс можно перенести на другой проект после этапа сопоставления схемы.

### Новые виды проверок

Контрольный сценарий хранит запрос, входы, прежний результат и измерения.
Дополнительный оценщик можно подключить через новый способ сравнения, сохранив
формат сценария.

### Параллельная обработка

Диалоги одного пользователя можно анализировать независимо. Каталог памяти имеет
блокировку на время консолидации и публикации. Для роста числа пользователей
потребуется очередь заданий и отдельное хранилище состояния запусков.

## Результаты опытов

### Синтетическая команда

Набор включает восемь диалогов четырёх участников:

- Анна: сверка заявочных и денежных показателей;
- Борис: исторические срезы и задержка данных;
- Вера: оценка правил и пересмотр меток;
- Денис: общие требования и различия определений.

Каждый диалог содержит четыре пользовательские реплики. Полный набор даёт
32 реплики плюс ответы модели и сообщения инструментов.

### Контрольная задача Анны

Во всех вариантах помощник получил основные значения:

- 8 заявок в когорте;
- 3 одобренные заявки на срез;
- 27 000 рублей заявочной суммы;
- 47 000 рублей выдач;
- 23 000 рублей возвратов;
- 24 000 рублей чистого денежного потока;
- нулевой остаток объясняющих мостов.

### Сравнение вариантов памяти

| Вариант | Время | Входные единицы текста модели | Выходные единицы | Ходы модели |
|---|---:|---:|---:|---:|
| Исходные данные, память отсутствует | 275 секунд | 2,30 млн | 59 724 | 72 |
| Только личные правила и контекст | 532 секунды | 0,50 млн | 39 786 | 24 |
| Только предметные знания | 681 секунда | 3,30 млн | 69 995 | 86 |
| Полная память | 422 секунды | 7,67 млн | 69 843 | 145 |

Эти значения относятся к одному запуску каждого варианта. Задержка OpenRouter
заметно менялась между запусками. Для статистического вывода потребуется серия
повторений.

### Причина большого расхода полной памяти

Первый запрос каждого варианта имел почти одинаковый размер: около 7,9 тысячи
единиц текста. Полная память увеличила путь выполнения после начала работы.

В полном варианте правильные числа появились примерно на 72-м событии. После
этого помощник выполнил ещё 109 обращений к модели и 108 действий инструментов.

Причины:

- одни требования повторялись в пользовательском запросе, `AGENTS.md`, справочнике и полном процессе;
- полный процесс требовал несколько дополнительных проверок и артефактов;
- критерий завершения допускал широкое продолжение работы;
- файловые инструменты получали разные формы путей Windows;
- помощник несколько раз перечитывал собственные SQL и отчёты;
- каждый следующий запрос включал накопленную историю.

После опыта описания процессов были переработаны. Каждый файл сохранил полный процесс большой
задачи. Этапы теперь создают явные промежуточные результаты, развилки включаются
по наблюдаемым условиям, а итоговая приёмка использует уже полученные доказательства.

## Ограничения и риски

### Прослеживаемость после смыслового анализа

Отчёты анализа имеют свободную форму. Точный идентификатор исходного сообщения
сейчас сохраняется в истории, а связь с отдельным пунктом памяти требует ручного
поиска по журналу запуска.

### Командное подтверждение

Текущий командный этап объединяет отчёты и публикует их после проверки модели.
Формальная процедура подтверждения несколькими сотрудниками находится в плане.

### Чтение командной памяти рабочими помощниками

Решающий помощник читает память своей рабочей области. Корневой командный каталог
требует копирования или подключения к пользовательской области. Автоматическое
распространение входит в следующий этап.

### Публикация нескольких файлов

Система сохраняет резервные копии и восстанавливает данные при исключении.
Читатель, обратившийся во время последовательной замены нескольких элементов,
может кратко увидеть смешанное состояние. Версионный каталог с одной ссылкой на
активную версию решит эту задачу.

### Повторяемость работы модели

Одинаковый запрос способен привести к разному числу шагов. Для научного сравнения
нужны повторные серии, одинаковые входы, единая модель, фиксированная версия
инструкций и статистическая обработка.

### Работа с путями Windows

Командная строка использует физические пути Windows. Файловые инструменты используют
виртуальные пути рабочей области. Единая функция преобразования путей сократит
ошибочные попытки.

### Конфиденциальность

Истории могут содержать персональные сведения, внутренние документы и секреты.
Для производственной версии потребуются правила доступа, удаление чувствительных
фрагментов, сроки хранения, журнал обращений и согласование публикации.

## Возможная научная постановка

### Объект исследования

Долговременная личная и командная память ИИ-помощников, автоматически создаваемая
из рабочих диалогов.

### Предмет исследования

Методы разделения, проверки и публикации знаний, которые сохраняют полезность,
прослеживаемость и переносимость между задачами и пользователями.

### Основной вопрос

Как превратить историю взаимодействия человека с ИИ-помощником в проверяемую
командную память, которая повышает качество решения новых задач при управляемых
затратах?

### Рабочие гипотезы

1. Разделение личной памяти, справочника, карточек опыта и полных процессов
   повышает точность применения знаний.
2. Проверка всей предлагаемой версии памяти снижает число противоречий и ложных
   обобщений.
3. Контрольная задача до публикации выявляет изменения, которые выглядят разумно
   в тексте и ухудшают практический результат.
4. Реестр происхождения и командное подтверждение повышают доверие к общей памяти.
5. Условное чтение материалов и явные этапы процесса снижают расход модели при
   сохранении полноты решения.

### Что можно измерять

- правильность ответа;
- полноту обязательных артефактов;
- число найденных противоречий;
- долю утверждений с прослеживаемым источником;
- число обращений к модели;
- число действий инструментов;
- объём входного и выходного текста;
- время выполнения;
- число повторных объяснений пользователя;
- успешность переноса процесса на другой проект;
- согласие экспертов с опубликованной памятью.

### Схема будущего опыта

Для каждой задачи выполняются несколько повторов в одинаковых условиях:

1. исходные данные и чистый контекст;
2. личная память;
3. предметные знания;
4. полный набор памяти;
5. полный набор памяти с реестром происхождения и условным чтением.

Эксперты оценивают правильность и полезность результата. Система автоматически
собирает время, объём обращений и действия инструментов.

## Что представить руководителю

Проект уже демонстрирует полный технический путь:

```text
чат -> два вида анализа -> копия памяти -> проверка -> контрольная задача
-> сравнение -> публикация -> командный каталог знаний
```

Главный следующий шаг связан с доказательностью командной памяти. Реестр
происхождения свяжет каждый опубликованный пункт с исходными сообщениями.
Промежуточный слой кандидатов добавит подтверждение участников и управление
конфликтами. Серия повторных опытов даст статистическую оценку качества и затрат.

После этого проект получит основу для конференционной работы: описанный метод,
