Уточнение от 24 октября: ближайшие изменения личного цикла описаны в
[спецификации](../openspec/specs/single-user-memory/spec.md). Сначала разделяем
анализ на два прохода, убираем split_report и даём ревьюеру исправлять копию.

зафиксированы там как отложенные задачи. Ниже сохранён ход предыдущих шагов.

## Что удалить

Первый пункт реализации — очистка. Старые реализации не архивировать внутри
проекта и не поддерживать через дополнительные переключатели.

### Код

- analyze_chats_manually.py и consolidate_reports_manually.py: второй путь
  анализа и консолидации, который пишет память напрямую.
- parse_arguments и run_agent из memory_pipeline.py: используются только
  перечисленными старыми скриптами.
- validate_knowledge_links из memory_pipeline.py: вызовов в Python-файлах
  проекта не найдено; оценка ссылок уже поручена LLM.
- Импорты, оставшиеся без применения после удаления этих функций.
- agents/consolidation/skills/init-llm-wiki/: текущий Codex-путь не подключает
  этот skill; создание wiki описано в используемых skills.
- Обработку прежнего раздела methods в split_report после проверки, что
  используемые session-*.md уже содержат skill. Если нет — сначала обновить
  нужные отчёты, затем удалить совместимость.

### Временные файлы

Удалить служебные выгрузки _dump_meta.txt, _dump_msgs.txt, _dump_tr.txt,
_tail.txt, _tmp_session.txt, _tmp2.txt, _tmp3.txt и tmp/dump_calls.py.
Назначение файла 0 проверить перед удалением: имя само по себе не доказывает,

### Документация

Переписать README.md и OPEN_IN_PYCHARM.md под текущие Codex-команды.
Переписать docs/memory-pipeline.md и docs/chat-database.md без инструкций запуска
удаляемых скриптов. В README сейчас описаны также уже отсутствующие модули и

После переноса нужных требований в актуальное описание удалить устаревшие

## Порядок реализации

### 1. Очистить текущий путь

Выполнить удаления выше, исправить инструкции запуска. Не переименовывать
оставшиеся скрипты ради оформления. Сохранить один путь анализа и консолидации
через Codex.

Результат: нет второго пути, который обновляет память в обход ревью.
Проверка: компиляция Python, существующие тесты, validate-only для Анны и Бориса.

### 2. Выделить используемые операции запуска

Вынести поиск CLI и запуск Codex в codex_client.py, переиспользовать из анализа,
консолидации и оценщика. Сохранять события, токены при их наличии и время процесса.

Вынести сборку решающего агента и сохранение сообщений в agent_runtime.py.
Использовать его из main.py, синтетических диалогов и проверочного прогона.
Агент прогона должен собираться так же, как агент пользователя.

Убрать привязку анализатора и консолидации к одному run_id из октября:
использовать явно переданную рабочую область.

Результат: одна реализация запуска для каждого применяемого типа агента.
Это перенос существующих операций, а не система адаптеров для разных платформ.

### 3. Готовить всю память пользователя в копии

Разделить consolidate_with_review на подготовку копии, ревью и перенос.
Сейчас она сама переносит результат сразу после ревью; до добавления прогона
эту связь нужно разорвать.

Личный этап готовит совместно:

- AGENTS.md и USER_PREFERENCES.md;
- user_llm_wiki/ с контекстом пользователя;
- knowledge/wiki/, knowledge/cases/, knowledge/skills/ и knowledge/INDEX.md
  внутри области пользователя.

Личные разделы отчётов получает skill consolidation, definitions/cases/skill —
skill consolidate-knowledge. Оба изменяют соответствующие файлы одной предложенной
версии пользователя. Ни один результат не переносится до общего решения.

Сохранить вне области переноса chat_logs.db, raw и исходные файлы задач.
Существующие пользовательские skills не удалять и не переписывать автоматически.

Результат: предложения можно применить агенту и отклонить без изменения оригинала.

### 4. Добавить один прогон и выбор варианта

Добавить replay_evaluation.py, skill оценки результатов и --evaluate-by-replay.

Вход: запрос, исходные файлы до решения задачи, предложенная память, прежние
ответы и итоговые файлы для оценщика. На первом этапе использовать один
подготовленный сценарий; симулятор пользователя не создавать.

Выполнить один новый прогон. LLM выбирает между прежним состоянием памяти и
предложенной копией по качеству результата и доступным измерениям. Повторов,
перебора комбинаций изменений и дополнительных вариантов памяти нет.

Если принята копия — перенести её. Если выбран прежний вариант, результат
неясен или прогон не завершён — сохранить материалы без переноса.
Выключенный флаг сохраняет путь принятия по ревью; такой результат не получает
статус проверки прогоном.

Результат: один полный личный цикл от отчёта до выбора памяти.
Проверка: один реальный прогон Анны; сохранность оригинала при отказе и сбое.

### 5. Добавить состояния командных сведений

Добавить team_memory.py и инструкции агенту управления командными сведениями.
Они описывают сопоставление, подтверждения и противоречия в переданных каталогах.

Вход: принятые изменения definitions/cases/skills пользователя с условиями,
статусом прогона и служебными идентификаторами диалогов. Не вся личная wiki.
При нескольких отчётах идентификаторы должны сохраняться раздельно: сейчас
код просто объединяет тексты, чего недостаточно для учёта подтверждений.

Использовать knowledge/ как действующий общий каталог и добавить:

```text
team-memory/pending/
team-memory/conflicts/
team-memory/registry.json
```

Правила: одно подтверждение — pending; подтверждение в другом диалоге —
допуск в общие знания; противоречие в одинаковых условиях — оба варианта
в conflicts с исключением спорного знания из применения.

Смысл и конфликт определяет LLM. Код учитывает идентификаторы, сохраняет
состояния и применяет принятое решение. Повторная обработка того же диалога
и проверочный прогон не добавляют подтверждений. Дополнения оцениваются
отдельно от ранее подтверждённой части.

Подготовку изменений общего каталога, pending, conflicts и реестра защищать
одной командной блокировкой и проверять до переноса. Иначе каталог и число
подтверждений могут разойтись. Повторного решения задачи на командном этапе нет.

Результат: сведения не публикуются сразу из одного чата, спорные не остаются
действующими. Текущим 12 файлам нельзя назначить подтверждения без сопоставления
с отчётами — выполнить это при подготовке первой версии нового реестра.

### 6. Подключить общие знания к решающему агенту

Агент получает личные правила, предпочтения и контекст, личный каталог знаний
и действующий общий каталог. Навигация — INDEX.md и файловые инструменты.
Pending и conflicts не передавать как действующие инструкции.

Результат: другой пользователь может применить накопленный опыт.
Проверка: один из существующих H-сценариев в docs/examples/synthetic-team/holdout.md.

### 7. Выполнить сквозную проверку

Использовать существующие диалоги и файлы команды, не создавать новый корпус.
Проверить:

1. Принятая личная память содержит определения, cases и skills.
2. Отклонённая личная копия не переносится.
3. Первое сведение попадает в pending.
4. Подтверждение в другом диалоге переводит его в общие знания.
5. Повторная обработка того же отчёта не увеличивает счётчик.
6. Противоречие снимает спорное знание с применения и сохраняет оба варианта.
7. Разные условия не превращаются в ложный конфликт.
8. Новое подтверждение позволяет повторно рассмотреть конфликт.
9. Другой пользователь использует общие знания с сохранением личных настроек.

Проверки содержания выполняет LLM. Тесты кода проверяют управление запуском,
состояниями, идентификаторами и переносом файлов.

## Что не добавляем на этом этапе

Очередь и расписание, версии публикаций с активным указателем, векторный поиск,
несколько реализаций подключения внешних агентов, отдельные сервисы, повторные
серии прогонов, генерацию многих вариантов и цикл повторных ревью.

Одно ревью с правом исправления копии включено в ближайшую версию по уточнению
от 24 октября.

Существующую блокировку и восстановление при обычной ошибке сохраняем.
Неперенесённые изменения и неразрешённые вопросы сохраняются для рассмотрения.
