# Восстановление состояния сущности на дату знания

## Когда применять

Нужна ровно одна строка на сущность с состоянием, известным на момент `T`, по истории событий: несколько исторических записей на сущность, часть записей появилась в хранилище позже своего бизнес-события. Дополнительно может требоваться пересчёт того же бизнес-времени с учётом поздних загрузок. Если нужны агрегированные показатели, они считаются по готовому срезу, а не по строкам событий.

## Вход

- Таблица сущностей с ключом и временем регистрации; границы когорты (нижняя включается, верхняя нет).
- История событий с бизнес-временем (`occurred_at`), временем загрузки (`loaded_at`), статусом и полем устойчивого порядка при равном времени (`event_id`).
- Значение `T` в той же временной зоне, что и данные.
- Действующая версия определения: включаются ли тестовые записи, какие статусы считаются финальными.
- Документированное правило выбора при равном времени; при его отсутствии — решение, которое нужно зафиксировать в артефакте.

## Алгоритм

1. Выписать `T`, границы когорты и версию определения в один `params`-CTE, чтобы они не были разбросаны по запросу.
2. Отобрать когорту по времени регистрации в полуинтервале `[начало, конец)`.
3. Отфильтровать события: `occurred_at < T AND loaded_at < T`. Оба предиката обязательны.
4. Выбрать по сущности первую строку в порядке `occurred_at DESC, <tie-break> DESC` через `ROW_NUMBER() OVER (PARTITION BY <ключ> ORDER BY ...)`. Порядок обязан быть полным: при равном времени без второго поля выбор недетерминирован.
5. Соединить срез с когортой через `LEFT JOIN` по ключу сущности, чтобы сущности без событий не исчезли; отсутствие известных записей оставить отдельным состоянием «неизвестно» (`NULL`), а не значением по умолчанию.
6. Для истории меток расследования применить то же правило к `recorded_at`, тай-брейк `label_id DESC`.
7. Агрегировать метрики уже по одной строке на сущность; в каждой публикуемой доле указывать числитель, знаменатель, период когорты, дату среза и версию определения.
8. Сохранить таблицу состояний и, если запрошено, SQL и краткие выводы.

## Проверка

- `COUNT(*) = COUNT(DISTINCT <ключ>)` в срезе; число строк после `LEFT JOIN` равно числу сущностей когорты, ни одна сущность не потеряна.
- Среди решающих записей нет ни одной с `occurred_at >= T`, и нет ни одной с `loaded_at >= T`.
- При равном времени выбор определён тай-брейком, а не физическим порядком строк; на сущности с ничьей это показано.
- Повторный прогон даёт идентичный результат; порядок строк зафиксирован `ORDER BY`.
- Отдельно посчитано, сколько записей отсечено только фильтром `loaded_at`: это число объясняет расхождение с «сырой» историей.
- Если проверка чувствительности валидатора уместна (есть риск, что проверка кардинальности тавтологична) — однократно прогнать её на наивном соединении с полной историей: она должна упасть. Без такого триггера негативный контроль не входит в обязательный набор.

## Условные действия

- **Нужен пересчёт прошлого с поздними загрузками** → второй режим без фильтра по `loaded_at` при той же границе `occurred_at`, плюс diff-запрос, оставляющий только расхождения, с колонками «что изменилось» и «по какой причине» (поздняя загрузка / иное). Режим маркируется при публикации и не подменяет исторический срез.
- **Запись имеет `occurred_at < T`, но `loaded_at >= T`** → исключить из среза и явно показать сущность и её состояние, на которые это повлияло.
- **Предлагают `DISTINCT` как исправление** → показать контрпример, где дублей ноль, а ответ неверен (ответ зависит от списка колонок; `DISTINCT *` при уникальном `event_id` не дедуплицирует ничего).
- **Есть равные времена события у одной сущности** → проверить, что порядок полон и включает устойчивый tie-break; привести конкретную сущность с ничьей.
- **Проверяют вариант фильтра по одной оси** → показать, есть ли в данных строки, различающие варианты; если различающих строк нет, корректность утверждается структурно (оба предиката + полный порядок) и это отмечается явно.
- **У сущности нет известных событий на `T`** → оставить состояние «неизвестно» и не подставлять `legitimate`, `rejected` или иное значение по умолчанию.
- **В срезе присутствуют тестовые записи** → выбрать версию определения (включать или нет) и указать её в результате.
- **Счётчики связанных строк (события, платежи, метки) считаются одним запросом с несколькими `LEFT JOIN`** → заменить на независимые подзапросы или предварительно агрегировать каждую связь до одной строки; проверить фактические счётчики, а не наличие связи 1:N.
- **Результат сохраняется в файл** → один раз проверить, что файл есть и читается. Размер и число ожидаемых блоков сверять, если есть подозрение на обрезание (наблюдаемое усечение, большой объём записи), содержимое — при изменении запроса или расхождении с ожидаемым; переводы строк CSV приводить к исходным, только если этого требует потребитель.

## Результат и завершение

Работа закончена, когда срез 1:1 по ключу, все проверки пройдены, агрегаты согласованы с построчным результатом, а неизвестные исходы обозначены явно. Артефакты: SQL среза с параметрами, таблица результата; при запросе пересчёта — diff двух режимов с указанием причины по каждой расходящейся сущности. Нерешённые вопросы (например, неподтверждённый статус отдельной сущности) перечисляются явно.
