# Case: диагностика расхождения двух отчётов — три гипотезы и атрибуция по сущностям

## Узнаваемая ситуация

Одна и та же сущность имеет разные статусы в двух отчётах: «исторический» показывает состояние, известное на границу `T`, «пересчёт прошлого» — состояние на ту же границу бизнес-времени, но с учётом поздних загрузок (это не «состояние сегодня»). Записи имеют две временные оси (`occurred_at`, `loaded_at`). Нужно установить механизм расхождения, не путая его с другими причинами.

## Исторический пример

- **Задача и условия:** заявка A006, `T = 2026-10-03 00:00:00 UTC`; исторический отчёт — `manual_review`, пересчёт — `approved`. Входы: `decision_events` (`event_id`, `status`, `occurred_at`, `loaded_at`), `applications`, словарь с правилом среза.
- **Что сделали:** до анализа зафиксировали семантику времени: снимок на `T` = `occurred_at < T AND loaded_at < T`, затем первая строка по `occurred_at DESC, event_id DESC`; пересчёт — тот же выбор без фильтра `loaded_at`. Построили линию A006: event 8 `manual_review` — occurred 2026-10-02 09:10, loaded 09:11; event 9 `approved` — occurred 2026-10-02 23:00, loaded 2026-10-03 03:00.
- **Как проверили:** H1 (событие ещё не произошло) — сравнили `occurred_at` с `T`, игнорируя `loaded_at`; H2 (произошло, но не загружено) — проверили `occurred_at < T <= loaded_at`; H3 (неверно выбрана запись) — проверили наличие ничьих и устойчивость выбора. Посчитали строки в разрыве `occurred_at < T <= loaded_at`, построили оба режима для всех 8 заявок и атрибутировали механизм каждой. Отдельно проверили tie-break на A007 (события 10 и 11 с равным `occurred_at` 2026-10-02 10:10:00).
- **Что получили:** для A006 подтверждена H2: 23:00 < 00:00 < 03:00, ровно одна строка в разрыве (event 9), задержка загрузки 240 мин. H1 для A006 опровергнута. Для A001 — H1: событие `occurred_at` 2026-10-04 08:00 позже `T`, поэтому между двумя режимами A001 не расходится; различие возникло бы только при сравнении с состоянием без границы `occurred_at < T`, и это законное различие, а не дефект данных. H3 для A006 не подтверждена: ничьей нет, любой порядок даёт event 8; на A007 правильный порядок даёт `rejected` (event 11), обратный — `approved` (event 10). Итог по снимку: фактическое различие двух режимов — одна заявка из восьми (A006). Метрики разделены: длительность бизнес-проверки 830 мин (09:10 → 23:00) и задержка загрузки 240 мин — разные оси, не складываются.

Это сведения о прошлой записи: перед использованием каталог проверяется на доступность в текущем окружении.

## Условия переноса

Переносится на сущности с историей событий и задержкой загрузки. Условия: две временные оси, явная граница `T`, документированный порядок выбора при равенстве времени. Ограничение: механизм атрибутируется отдельно по каждой сущности — одинаковый симптом может иметь разные причины. Вывод о «пакетной догрузке» по одному выбросу — согласующееся, но слабое свидетельство; отдельно проверяется расписание загрузки. Обходной путь отделяется от исправления: дефект A006 — отсутствие объявленного режима в отчёте, а не неверные данные.
