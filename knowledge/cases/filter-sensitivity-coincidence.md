# Case: совпадение ответа не доказывает корректность временного среза

## Узнаваемая ситуация

Запрос даёт «правильный» ответ на конкретном снимке, но по совпадению: альтернативный неверный вариант фильтра проходит только потому, что в данных нет различающих строк. Возникает при проверке временных срезов и при подгонке запроса под ожидаемую цифру.

## Исторический пример

- **Задача и условия:** проверить корректность среза, не меняя правила ради совпадения чисел; заявка A006 при `T = 2026-10-03 00:00:00 UTC`.
- **Что сделали:** сравнили результат и счётчики строк для трёх вариантов фильтра — только `occurred_at < T`, только `loaded_at < T`, оба предиката; проверили, есть ли в снимке строки с `occurred_at ≥ T > loaded_at`, различающие варианты.
- **Как проверили:** выполнили все три варианта, получили счётчики 12 / 11 / 11 строк и статус A006: `approved` / `manual_review` / `manual_review`.
- **Что получили:** вариант `occurred_at only` дал `approved` — использовано знание будущего. Вариант `loaded_at only` дал `manual_review` — верно случайно, поскольку единственное событие с `occurred_at ≥ T` (event 13) имеет и `loaded_at ≥ T`, то есть различающих строк в снимке нет. Оба предиката — верно структурно. В смежном прогоне легаси-агрегата тот же эффект: `COUNT(*) = 6` совпал с числом заявок лишь потому, что ни у одной заявки нет двух `approved`-событий; при повторном одобрении после `manual_review` заявка посчиталась бы дважды. Правила среза не менялись.

## Условия переноса

Применять при любой проверке среза: сравнить варианты фильтра и установить, различают ли их данные. Если различающих строк нет, корректность доказывается структурно (оба предиката + полный порядок выбора) и это явно отмечается; результат отдельного снимка доказательством не является. Совпадение числа с ожиданием не считается подтверждением корректности запроса.
