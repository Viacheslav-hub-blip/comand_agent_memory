# Срез «известное на T» и пересчёт прошлого — разные режимы с разными условиями времени

- Ситуация: нужно состояние сущности, «которое можно было увидеть в хранилище
  к моменту T», и/или пересчёт на то же бизнес-время с учётом всех уже загруженных
  записей. У записи есть бизнес-время (`occurred_at`) и время появления
  в хранилище (`loaded_at`).
- Причина: фильтр только по бизнес-времени пропускает записи, загруженные после T,
  и они задним числом меняют прошлое; фильтр только по времени загрузки пропускает
  записи с будущим бизнес-временем, загруженные раньше T. Ни одно условие
  по отдельности не покрывает оба случая. Два режима различаются только условием
  на `loaded_at`, но дают разные цифры; смешение режимов искажает отчёт.
- Решение: для режима знания — `WHERE occurred_at < T AND loaded_at < T`; для
  пересчёта — только `occurred_at < T`, без ограничения `loaded_at`. Дальше свёртка
  до одной строки документированным порядком. Реализовать два запроса (или два CTE),
  различающиеся только этим условием, и при запросе сравнения выводить только
  расхождения; состав сущностей в обоих режимах одинаков. Правила среза не подгонять
  под совпадение цифр.
- Проверка: сущность с записью `occurred_at < T`, но `loaded_at > T`, при двойном
  фильтре имеет одно состояние, а при снятии условия на `loaded_at` — другое;
  запись с `occurred_at > T` отсекается только условием на `occurred_at` и не
  попадает ни в один режим; обе реализации дают одинаковый набор расхождений.
- Границы: оба условия обязательны именно в режиме знания; пересчёт — не «текущий
  снимок целиком», без границы бизнес-времени в него войдут будущие события.
  Малая разница на конкретном снимке — свойство данных, а не гарантия. Без
  `loaded_at` историческое знание не восстановить.

## Разбор расхождения без объявления «данных нет навсегда»

Три различимых механизма расхождения по одной сущности: H1 — запись ещё
не произошла (`occurred_at >= T`); H2 — произошла, но не загружена
(`occurred_at < T AND loaded_at >= T`); H3 — реализация неверно выбрала последнюю
запись. Проверять по порядку: классифицировать записи по двум временам, убедиться,
что запись существует и `loaded_at` конечен, сравнить оконный выбор с независимым
`argmax`, проверить полноту ключа порядка и одинаковость состава когорты.
Отсутствие записи при «нет данных» требует отдельного подтверждения владельцем;
задержку нельзя выдавать за окончательное отсутствие данных.
