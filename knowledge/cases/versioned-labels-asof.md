# Срез версионных меток на дату знания вместо соединения со всей историей

- Ситуация: у заявки есть первоначальное и исправленное заключение. При соединении
  срабатываний правил со всей таблицей меток заявка размножается и может попасть
  одновременно в TP и FP; текущий снимок привносит в прошлую оценку будущее знание.
- Причина: таблица меток — история версий, а не уникальный справочник. Актуальная
  метка зависит от даты знания. Выбор последней строки без фильтра по времени записи
  задним числом меняет исход и метрики; соединение «один-ко-многим» размножает
  строки срабатываний.
- Решение: перед соединением строить срез «одна строка на заявку»: отфильтровать
  `recorded_at < T`, по каждой заявке выбрать последнюю версию; при равном времени
  использовать явно заданный тай-брейк (например, `label_id DESC`). Соединять
  срабатывания только с этим срезом; для каждой даты знания строить отдельный срез.
  Более поздние исправления в режим «как знали на `T`» не применять.
- Проверка: после среза одна версия метки на заявку; исправление, записанное после
  `T`, не попало в расчёт; одна и та же заявка на ранней дате учтена в TP,
  на поздней — в FP, но ровно один раз на каждой дате; `TP + FP + unknown = |hit_ids|`;
  метрики воспроизвелись из отфильтрованного среза.
- Границы: применимо для исторического as-of анализа. Пересчёт прошлого с учётом
  поздних корректировок — отдельный режим. Нужны надёжные `recorded_at`
  и детерминированное правило разрешения равного времени; если в хранилище есть
  отдельное время загрузки, срез знания должен учитывать и его. При отсутствии
  истории версий приём не нужен.
