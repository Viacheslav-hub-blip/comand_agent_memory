# Case: исторический снимок на T и пересчёт на то же бизнес-время

## Узнаваемая ситуация

Нужно разделить два вопроса: «что было известно на дату `T`» и «каким состояние оказалось бы, если учесть все поздние загрузки на ту же границу бизнес-времени». Смешение режимов делает метрику нестабильной: она меняется при каждой догрузке.

## Исторический пример

- **Задача и условия:** система «Заявки»; когорта `created_at` ∈ [2026-10-01 00:00:00, 2026-10-03 00:00:00), `T = 2026-10-03 00:00:00 UTC`. Режим A — знание на дату (`occurred_at < T AND loaded_at < T`), режим B — пересчёт (`occurred_at < T`, `loaded_at` не ограничивается). Таблицы `applications`, `decision_events`; локальная SQLite по `schema.sql` на CSV; результаты в `outputs/C02/`, исходники не изменялись.
- **Что сделали:** два независимых запроса, различающихся ровно одним условием; отдельный diff-запрос, соединяющий режимы и оставляющий только расхождения, с колонками `status_changed` и `different_by`; тай-брейк `occurred_at DESC, event_id DESC` одинаков в обоих режимах; срез до соединения через `ROW_NUMBER()`. Для режима A SQL сохранён как `snapshot_application_state.sql`.
- **Как проверили:** в каждом режиме 8 строк и 8 уникальных `application_id`; повторные прогоны идентичны; режим A побайтно воспроизвёл ранее сохранённый `application_state_snapshot.csv`; каждый CSV сверен с выдачей своего запроса построчно; пять проверок кардинальности с негативным контролем (см. [cardinality-negative-control.md](cardinality-negative-control.md)). Отдельно измерены три варианта фильтра: только `occurred_at` — 12 строк, только `loaded_at` — 11 строк, оба предиката — 11 строк.
- **Что получили:** различие режимов ровно одно — A006: `manual_review` (event 8) против `approved` (event 9), причина `late_loaded_event`: `occurred_at 2026-10-02 23:00:00 < T` при `loaded_at 2026-10-03 03:00:00 ≥ T`, задержка загрузки 240 мин. A001 расхождения не даёт: событие 13 `rejected` с `occurred_at 2026-10-04 08:00:00` позже `T` и отсекается в обоих режимах — это подтверждает, что B есть пересчёт на то же бизнес-время, а не «состояние сегодня». A007 — единственная заявка с ничьей по `occurred_at` (event 10 `approved` / event 11 `rejected`, 2026-10-02 10:10:00), при `event_id DESC` побеждает `rejected`. Метрики: `approval_rate` 2/7 = 28,57 % → 3/7 = 42,86 %; `final_decision_approval_rate` 2/4 = 50,00 % → 3/5 = 60,00 % (знаменатель изменился, потому что A006 вошёл в финальные решения); запрошенная сумма одобренных 22 000 → 30 000 ₽. Длительность бизнес-проверки A006 — 830 мин (09:10 → 23:00), это другая ось и с задержкой загрузки 240 мин не складывается. Собственная арифметическая ошибка (75,0 % вместо 60,0 %) была поймана SQL-проверкой.

## Условия переноса

Две временные оси, явная граница бизнес-времени, одинаковая для обоих режимов, документированный полный порядок выбора при равном времени. Различие режимов — только фильтр по времени загрузки. Режим пересчёта обязательно маркируется при публикации; для отчёта на дату среза публикуется режим исторического знания. Механизм расхождения атрибутируется по каждой сущности отдельно.
